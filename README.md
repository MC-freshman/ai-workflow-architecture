# AI Workflow Architecture · 多平台 AI 工作区与架构管理台

公开资源与源码发行仓。适合想使用或研究这套架构、建立自己工作区的用户。

这套架构让你在不同 AI 客户端里复用同一套**专家、工作流、技能和软件调用规则**。例如，你在一个客户端使用软件工程专家分析项目，换到另一个客户端时，仍可选择同一版本的专家和依赖，通过可校验的项目交接继续工作。资源更新有版本，执行有记录，失败可以定位和恢复。

**Architecture Manager（架构管理台）0.8.3** 是配套的 Windows 桌面管理工具：它帮助你查看资源、准备平台接入、发布版本、执行统一更新和核对结果。AI 模型、账号与厂商客户端仍由你自己准备；管理台不会因为安装成功就替你获得模型能力或第三方软件授权。

## 1. 先认识这套架构

### 它解决什么问题

如果你只有几条临时提示词，直接在聊天里使用就可以。下面这些需求更适合这套架构：

- 多个 AI 客户端反复安装相同的专家、技能和工作流，内容很容易变成不同版本。
- 想知道一次任务用了哪个专家、哪个流程、哪些技能，而不只是“用了最新版本”。
- 一项任务需要按阶段处理输入、产出文件、自检、调用脚本或软件，并在中断后继续。
- 更新了资源，希望新任务采用新版，进行中的任务继续使用原来锁定的版本。
- 希望由图形界面完成配置和版本管理，出错时能看见具体卡点，保留可回滚的记录。

### 有哪些功能

| 功能 | 对使用者的具体作用 |
|---|---|
| 共享资源目录 | 同一份专家、流程、技能和配方供多个平台只读使用，不为每个平台重新维护一份正文 |
| 版本和依赖锁 | 保留旧版；为新版本建新目录；新任务选版后固定依赖，途中不静默换版 |
| 分阶段执行 | 按工作流返回的动作执行、提交结果并接受检查；遇到缺输入、失败或取消留下实际状态 |
| 平台隔离 | 每个客户端有自己的配置、环境、软件安装位、凭据和运行记录，互不借用私有状态 |
| 软件接线 | 通过配方、实际本体和 CLI/GUI/MCP 接口调用软件；先明确能力、参数、边界和授权 |
| 管理台 GUI | 只读盘点、导入资源、预览变更、确认执行、平台接入、统一更新、停止/继续/恢复 |
| Git 与备份 | 保存治理和可入库配置；扫描后正常推送；不可入库的环境和本体另作平台备份并核对恢复 |
| 跨客户端续跑 | 经带 SHA-256 的交接载体回读项目状态、核对版本，再接着做下一段工作 |

**“平台”在这里指运行客户端及其本地适配环境**，如 Codex、Qoder、WorkBuddy、ZCode 等。一个客户端的安装目录、MCP 配置或平台文件夹存在，不能单独证明它已经接入。

**共享架构、管理台应用和 AI 客户端是三个不同的东西**：架构规定资源怎样组织和执行；管理台负责维护这套工作区；AI 客户端中的模型负责它获准执行的推理、写作、编码等任务。

## 2. 为什么有 tool、agent、software 三个仓

这里的“三仓”是工作区中的三个共享资源目录。它们可以由同一个 GitHub 仓库托管；本项目的“公开仓/私有仓”是发布与维护的 Git 仓库，和这三个功能目录不是同一个分类。

| 名称 | 放什么 | 怎样使用 | 不放什么 |
|---|---|---|---|
| `tool/` | 工作流定义、提示词/脚本、输入输出 schema、技能 skill、能力包 pack，以及执行引擎和治理工具 | 工作流规定任务的阶段与动作；技能提供可选场景或方法；引擎负责解析、派发和检查 | 模型账号、软件安装包、虚拟环境、日志和业务运行结果 |
| `agent/` | 专家角色、提示词、策略、主工作流及精确依赖锁 | 选择专家后，按它的 `tool-lock` 使用指定工作流和技能 | 专家的个人会话、登录态、缓存和平台私有工作区 |
| `software/` | 软件配方、能力快照、接口 schema、获取/校验/启动规则和连接器/网关定义 | 由所属平台取得实际软件，验证后按声明接口调用 | 第三方 EXE、数据库、许可证密钥或真实用户数据 |

几个容易混淆的概念：

- **agent 是“由谁、按什么专业规则处理”**，不是一个自动常驻、自己拥有账号的程序。
- **workflow 是“按什么阶段处理”**。`tool` 是共享工作流仓的目录名，不意味着里面每个文件都能作为任意终端命令执行。
- **skill 是可复用的方法或场景内容**。它可以被工作流或专家按版本引用；本项目的共享技能与某个客户端的原生技能安装目录需要通过平台入口连接。
- **pack 是一组可共享能力或策略内容**，同样需要按声明和锁使用。
- **software recipe 是“怎样接软件”**。看到 nmap、数据库或浏览器类配方，不等于对应软件已经安装、登录或具备所有业务功能。
- **MCP/CLI/命令映射是接入通道**。它们把当前客户端的工具请求交给平台适配器，不代替专家和工作流本身。

### 一个实际例子

当前资源中，`software-engineer@1.8.0` 是软件工程专家，其精确锁选择 `se-pipeline@1.3.0` 和若干软件工程技能。

```text
你在 AI 客户端提出任务
    → 当前平台的命令/Skill/MCP 入口
    → 读取 agent：software-engineer 的角色和锁
    → 读取 tool：锁定的 se-pipeline 和相关技能
    → 为本次 run 固定版本与输入
    → next 返回阶段 → 客户端完成获准动作 → submit 提交
    → 检查通过后继续，直到成功、失败、停止或等待输入
```

如果某阶段声明需要外部软件，再从 `software` 解析配方，经过本平台的实际本体、环境、权限和接口校验后派发。没有这个依赖的纯提示词阶段，不会因为某个无关软件还没安装就自动失去全部使用资格；确实需要而未具备的动作必须明确拒绝并列待补。

## 3. 工作区、版本和运行记录怎样组织

```text
你的工作区/
├─ tool/                       共享工作流、技能、能力包和治理工具
├─ agent/                      共享专家及精确依赖锁
├─ software/                   共享软件配方，不含软件本体
├─ architecture-manager/       管理台源码；普通用户可直接用 EXE
├─ versions/                   架构原则、工作区接入登记与版本说明
├─ <你的平台>/                  经授权创建的平台目录
│  ├─ bridge.json / bridge/    本平台配置、入口与适配器
│  ├─ runtime/                环境、本体、运行锁、日志和证据
│  └─ workspaces/             活跃项目
└─ inbox/                     按平台登记的 backup、archive、trash
```

初次解压公开工作区时没有作者的已接入平台是正常的。你需要创建并验证自己的平台；上面的平台和 inbox 目录不是要求你随意手建、复制别人的配置。

三个共享仓都保留 `registry`、`current.json`、`versions/<语义化版本>/`、逐文件 `SHA256SUMS` 和依赖声明。技能等资源的具体位置以注册表解析为准，不靠扫描任意文件夹自动发现。

| 版本概念 | 含义 |
|---|---|
| 管理台版本 `0.8.3` | Windows 应用和它的源码/安装包版本 |
| 架构版本/基线 | 组织、隔离、契约和验收规则的一次演进；不是每个资源的版本号 |
| 各资源版本 | 每个 workflow、agent、skill、pack、配方各自发布的语义化版本 |
| 共享默认 `current` | 默认选哪个已发布版本；指针可以改，旧版正文不能覆盖 |
| 平台个人选版 | 某平台对未来任务的合法默认覆盖，不改其他平台或共享 current |
| 本次 run 的锁 | 本次实际采用的资源、依赖及解析来源；开始后不会跟着默认指针漂移 |

专家内部调用服从精确 `tool-lock`。把某个 skill 的共享默认改成新版，不等于一个锁定旧 skill 的专家会自动换版；需要发布并采用新的专家/工作流锁，才能明确使用新依赖。历史 run 继续按原锁续跑。

运行锁位于 `<平台>/runtime/runs/<run-id>/run-lock.json`，状态、事件和产物摘要也归本平台。准备好锁只是“准备完成”，成功必须有相应阶段结果和真实终态。

| [中文离线指南](https://github.com/MC-freshman/ai-workflow-architecture/releases/download/v0.8.3/Architecture-Manager-0.8.3-Guide.zh-CN.md) | 保存后离线阅读本文的主要操作和状态说明 |

EXE 是管理工具；要使用三仓资源，还需要工作区源码以及自己的 AI 客户端。解释器、Git、模型账号与业务所需软件按实际接入功能准备，不包含在一个 EXE 安装成功的结论里。

### 第一次使用的顺序

1. **获取工作区**。下载公开仓 `v0.8.3` 源码 ZIP，或使用下面的 Git 命令。选中解压后真正包含 `AGENTS.md`、`tool`、`agent`、`software` 的根目录，不要选 ZIP 的外层空文件夹。
2. **打开管理台并选择工作区**。先等只读扫描完成，在“资源”确认能看到三个共享仓的内容。
3. **创建或选择自己的平台**。到“平台与接入”，为实际客户端选择平台 ID；新增平台一级目录时明确确认。客户端程序必须是本机真实安装位置。
4. **准备配置与环境**。按向导核对解释器、模型上下文窗口及来源、运行目录、权限和实际需要的能力。不知道的信息保留待补，不填猜测值。
5. **预览“一键接入／继续”并确认**。管理台按计划准备可自动完成的配置和环境。登录、安装器、UAC、许可证和厂商确认由本人操作。
6. **加载客户端入口**。在厂商客户端打开对应项目/工作区，加载所登记的 MCP/命令/技能，核对真实工具是否可见；有些客户端需要重新加载项目或重启才能采用新配置。
7. **读取结果并验证**。分别看配置、能力、调用检查和原生回执。按下文判断现阶段能做什么，先做本平台、当前版本的最小调用验证，再做实际业务。

```powershell
git clone --branch v0.8.3 https://github.com/MC-freshman/ai-workflow-architecture.git my-ai-workspace
cd my-ai-workspace
python -B scripts/verify-checksums.py
```

`--branch v0.8.3` 得到固定发行快照；Git 可能处于 detached HEAD。需要维护自己的工作区时，再创建个人分支并配置自己的私有远端。不要把个人配置、runtime 或凭据推送给本公开上游；也不要用新源码 ZIP 覆盖已有生产工作区。

## 5. 接入到哪一步，才算能正常调用 agent / tool

下面是**判断证据的层次，不是平台永久分级**。每个平台最终应补齐同一套共享能力，不能拿别的平台通过记录代替自己的结果。

| 当前状态 | 它真正证明什么 | 此时可以做什么 |
|---|---|---|
| 目录已存在、配置已保存 | 文件已落盘，路径/字段已登记 | 继续准备和检查；不能据此称已接入 |
| 能读取三仓并校验释放版 | 三个 registry 可读；选中的版本和 SHA256SUMS 能回读 | 浏览定义、了解依赖、准备计划；还不能证明运行通道或模型工作 |
| 调用检查通过 | 用本平台配置，目标工作流/专家确实能 prepare→领取阶段→stop，依赖解析与检查所覆盖的入口成立 | 后端入口具备可调用证据；还要确认当前客户端确实能通过它调用 |
| 当前厂商原生回执通过 | 当前客户端/配置/服务/版本绑定下，真实工具通道读取了三仓冻结内容 | 可以把该入口交给客户端中的 AI 使用；按具体任务依赖验证业务动作 |
| 更新完成（调用验证通过） | 本次目标更新、调用覆盖、当前原生入口和该更新要求的 Git 收口满足 | 使用更新后的入口；这是更新结果，完整能力认证仍另看 |
| 完整接入认证通过 | 全三仓能力地板及规定的本平台完整认证、入口和登记满足 | 声称本平台完成当前架构接入；不等于所有未来业务都已经成功执行 |
| 某次业务 succeeded / 已交付 | 那次 run 所需阶段、检查、输出和终态有实际证据 | 报告那次任务的结果；不能外推为未测试软件或其他平台全部成功 |

### 开始用 AI 调用一个具体资源的实用条件

至少核对下面这些事实：

1. 当前平台的三仓根路径正确、可只读访问；所选 agent/workflow 和依赖存在、哈希有效、版本配对一致。
2. 本平台执行器和解释器可用，`runtime` 可写，共享释放版不能被执行过程写入；目标入口已实际通过调用检查。
3. 当前 AI 客户端已加载平台入口，能从真实工具返回读取资源和执行协议的结果。另一个终端的 CLI 自测不能代替当前客户端接通。
4. 任务实际需要的 profile、动作、脚本隔离、peer、软件本体/接口等已具备；缺哪项就限制哪项，不能让模型口述“成功”代替执行。
5. 模型账号可用、实际上下文窗口和任务输入满足要求。客户端中的 AI 按返回的 schema 填参数，按阶段执行和提交；缺必要输入时先补输入。

这时可以正常尝试符合该依赖闭包的任务，**不必等无关的全部外部软件都做完业务验证，才能使用一个已经就绪的纯提示词工作流**。但不能因此把尚有缺口的平台标成完整接入。

### wf 与 wfa 怎么用

支持且已安装本项目入口映射的客户端，可以用以下任务表达：

```text
$wf se-pipeline 草稿：分析这个项目的一处 API 缺陷，只做点名范围，不初始化已有项目。
$wfa software-engineer 草稿：按专家自己的主流程分析该缺陷，先说明需要的输入。
$wfa software-engineer@1.8.0 草稿：本次固定这个专家版本。
```

`wf` 直接选择工作流；`wfa` 选择专家，并服从专家内部精确锁，不由调用者另塞一条任意流程。省略版本时按有效默认解析；精确版本只影响本次 run。

`$wf/$wfa` 和 `/wf /wfa` 不是所有厂商都自带的原生命令。需要本平台相应 Skill/命令映射；如果没有，使用已经接通的 MCP/CLI 协议入口，或让平台维护者先安装映射。只有模型复述“已调用 wfa”而没有工具返回和 run 记录，不算真正调用。

管理台提供的 MCP 服务包含 `architecture_list`、`architecture_get_release`、`architecture_run`，以及平台版本读取/选版工具。客户端 AI 应先获取定义，再用 `architecture_run` 转发合法 runner 请求；不同平台入口名称可能由适配器映射，不能照抄别的平台私有启动路径。

未写档位按**草稿**范围执行；“过图”启用该流程的非严格 QA；“交稿”才执行该流程声明的完整交付检查并冻结。调用性检查不会替你完成业务模型输出，也不会授权 AI 清空已有项目。

## 6. 需要什么才能“完整接入”

完整接入的基本能力要求是：**共享侧集中计算的三仓能力并集，在本平台为 0 个 `declaredAbsent`**。实际检查还必须消除 `unverified`、缺来源/缺证据等问题；文件里写了 `supported=true` 不能替代证据。

| 必须满足的方面 | 要核对的实际内容 |
|---|---|
| 三仓和版本 | tool、agent、software 全部接线；释放版完整性与精确依赖有效；执行器、契约、扫描器等配对一致 |
| 能力地板 | 相同能力并集下本平台无 declaredAbsent、无未验证项；每项结果可回读，来源完整 |
| 脚本和权限 | 声明的 script/action/profile 有实际环境和隔离适配器；共享只读、平台写入、网络/进程边界按契约成立 |
| 委派等动作 | 如并集要求 peer/delegate，具备本平台 dispatcher 与真实接口证据，不能复制其他平台证明 |
| 软件面 | 实际本体/版本/哈希、冻结能力快照、参数 schema 和调用接口匹配；涉及登录、许可证和权限时真实满足条件 |
| 当前客户端入口 | 当前厂商客户端的注册和真实工具回执有效，配置/程序/服务/版本改变后重新核对 |
| 规定的完整认证 | 首次接入或引擎/契约大版本变化使用相应完整矩阵；不存在零行假绿、漏格或把局部调用覆盖当完整覆盖 |
| 治理和恢复 | 按既定接入 P 表保存锁、事件、摘要、治理/配置入库和必要恢复记录；备份实际恢复过 |

`conform` 报告中的 `pass` 是该能力项的证据满足，`declaredAbsent` 是尚未提供，`unverified` 是尚无可接受证据。缺口应记录原因、补齐路径和成本；它表示待补，不表示“这家平台永远不支持”。

完整矩阵也应按每一格实际证明的范围解释。软件行可以证明配方解析、快照和本体绑定，但不能凭这些就声称软件某个破坏性或 GUI 内部业务已经派发成功。实际业务动作仍需按真实接口、参数和当次授权执行。

需要 administrator/UAC 的能力可以按**每次调用的明确授权**提供；完整接入不要求客户端永久以管理员身份运行。主机执行降级也必须有当次同意，不能为了消除红项偷偷降低隔离。

新增或更新资源复用已经具备的 profile 时，通常做索引追加和受影响资源的单格检查。旧内容哈希不变就复用有效证据；不为普通 skill/agent 更新重复全平台认证。

## 7. 三仓接到什么程度，适合直接让平台里的 AI 继续接入

### 接入前：AI 可以帮你理解和拟定方案

只要当前客户端本身能读取你授权的工作区文件，就可以让 AI 阅读 README、盘点本机条件、列缺口和提出 P 表。此时它使用的是客户端原有文件/终端工具，属于**搭建或维护**，不能自称已经通过本架构的 agent/workflow 业务入口。

### 建议的交接点：三仓可读 + 当前平台入口可调用

当三仓 registry 和冻结释放版可读可校验，本平台 runtime 与执行器可用，目标入口通过 prepare→next/领取→stop，且当前 AI 客户端能使用真实 MCP/CLI/命令通道时，就适合把**继续接入和资源维护**交给这个平台中的 AI。

此时 AI 有能力依据真实定义和错误继续工作，不需要你手工拼接一堆提示词。完整能力并集尚未全部补齐也可以继续维护，但 AI 只能运行已具备能力的步骤：缺脚本隔离先准备隔离，缺软件本体先按配方安置和验证，缺厂商接口就登记并开发适配；不能用修改能力 JSON 的方式让检查“变绿”。

可以直接给它这样的任务：

```text
阅读当前工作区 README、AGENTS.md、AI_ARCHITECTURE_SYSTEM_PROMPT.md 和总手册。
只盘点并维护我的 <平台 ID>，用本平台实际配置读取 tool、agent、software。
先给出有序 P 表，说明每项缺口、依赖、验证方法和必须由我手操的步骤。
执行范围以我的明确授权为准。保留旧发布目录、版本锁和既有项目；
不要复制别的平台 runtime，也不要擅自切共享 current 或永久提权。
能自动完成的步骤实际执行，登录/UAC/厂商交互明确交给我；
完成后分别报告配置、调用能力、原生回执、完整接入和 Git/恢复结果。
```

**仍需本人处理**的常见事情是：选择/安装真实客户端，厂商账号登录、OAuth 和二次验证，UAC/系统安装，许可证确认，以及在客户端加载项目或接受它自己的工具确认。API 密钥由你通过本平台凭据设施提供，不能贴进公开 README、配方或 Git。

如果 AI 只能看见三仓正文，却没有真实执行通道，它可以协助搭建，不能代替运行验证；如果它有执行通道但没有某项能力，它可以补接和登记，不能把未执行的部分写成完成。

## 8. 一键更新所有平台、skill/agent 更新与恢复

### 统一更新怎样操作

1. 打开新版管理台，选择已有工作区，在“平台与接入”点击**一键更新所有平台**。
2. 核对统一预览中的平台、目标版本、依赖和保留的个人固定版本，点“确认并执行”。0.8.3 不再对这个计划弹第二个 Windows 确认框。
3. 各平台依次准备、更新和验证，结果独立保存。一个平台待补不会被另一个平台的绿行代替。
4. 需要本次远端收口时，勾选“同时正常推送已配置的 Git 远端”；同一工作区会沿用上次选择。未推送时可保留“调用已验证，待推送”，这不等于执行器一概不可用。
5. 查看配置、wf/wfa、完整接入、厂商原生工具四个结果。尤其不要把“更新完成（调用验证通过）”读成“所有软件业务已验证”。

这个按钮面向**已有有效接入配置**的平台。一个全新的空工作区应先完成平台创建和基本接线，不能期待更新按钮自动替你提供厂商账号、任意本体和不存在的接口。

### 发布一个新的 skill / agent / workflow

在“导入本体/资源”确认类型、ID、正文、版本、依赖和权限，预览后发布到新的版本目录。再选择共享默认或合法平台默认，检查受影响资源。已发布旧版和现有 run 不覆盖。

平台独立选版工具主要针对 workflow/agent；skill/pack 跟随依赖锁解析，不能假设它们也有一个任意平台默认覆盖开关。专家要采用新版技能，应发布新的专家依赖锁并明确采用；不靠改写旧 `tool-lock` 偷换依赖。

### 停止、继续和恢复

点击“停止本次操作”后，等进程树回收和安全写入收口；再从同一工作区继续。哈希一致、真实通过的格可复用，失败或变更格重验。恢复只还原本次操作拥有的配置/指针；外部并发改动需核对，不覆盖别人的新改。

跨客户端续跑使用带 SHA-256 的交接载体和版本一致性校验，在 **run 粒度**接续；不对正在运行的单个 run 做在线热迁移。平台内锁表不提供跨客户端互斥，两个客户端同时写同一项目副本可能互相覆盖，应由使用者避免。

## 10. 常见卡点怎么判断

| 现象/错误 | 先看什么，怎样处理 |
|---|---|
| 扫描看不到平台 | 新公开工作区没有个人平台；先到向导创建并接线，确认选中了真正根目录 |
| “配置已更新”但 wf/wfa 待验证 | 查看本平台的依赖、能力地板和调用格；先补实际阻断，不手改状态文件 |
| CLI 检查通过，但 AI 说找不到工具 | 当前客户端可能未加载 MCP/Skill/命令映射；打开对应工作区、重新加载，并从该客户端取得真工具返回 |
| `NATIVE_CLIENT_BINDING_CHANGED` / 原生回执待验证 | 程序、配置、服务或版本绑定已变；重新核对登记和当前回执，旧成功记录不能直接续用 |
| `CAPABILITY_UNAVAILABLE` | 缺本轮动作所需的环境/适配器/profile，按报告补接；不能把脚本改成模型口述来冒充执行 |
| `VERSION_CONFLICT` | 引擎/契约/扫描器或依赖锁未配对；按目标配对更新，保持在途 run 原锁 |
| `CONTEXT_BUDGET_EXCEEDED` | 核对真实窗口与任务范围；选更窄场景或分阶段/发布合理的新内容，不猜大容量、不截断旧版、不关闭预算检查 |
| 软件显示未验证 | 检查真实本体、版本/哈希、冻结快照、接口和证据；不是简单给六个名字统一填 true |
| “已验证，待推送” | 核对自己的 Git 远端、身份、授权和扫描结果，再继续正常推送；不要强推公共上游或混入凭据 |
| 取消后继续重复全检 | 应先读取本次所属进程的清理记录和哈希绑定来源；0.8.3 已修复已知中断复用问题，变更过的格仍须重验 |

## 11. 开发、文档与许可

普通用户使用 Windows EXE 即可；源码开发需要 Node.js 24+、npm 和对应平台环境。

```text
cd architecture-manager
npm ci
npm start
npm run conform -- --out <你自己的检查输出目录>
npm run package:win
```

开发 `conform` 检查应用质量，平台能力 `conform` 检查三仓能力在某个平台的兑现情况，两者用途不同。测试或构建输出保存到自己的平台临时/维护目录，不能写进冻结资源。

本文已经给出了主要用途、操作和判据。进一步的界面细节、结构和发行材料可读 [快速开始](docs/quick-start.md)、[使用手册](docs/user-guide.md)、[架构说明](docs/architecture.md)、[0.8.3 发行说明](docs/releases/0.8.3.md)；它们是补充，不是理解本项目的前置跳转清单。

公开架构内容保留已有 MIT（代码）/CC-BY-4.0（文档与定义）声明，各第三方目录的 LICENSE/NOTICE/SOURCE 优先。管理台源码尚无单独新增开源许可；公开托管不自动授予一切再分发权，具体按仓库 LICENSE 的范围处理。

反馈时提供应用版本、平台、资源 ID/版本、步骤和脱敏错误摘要。不要上传整份 runtime、备份、模型密钥、登录轨迹或项目私密数据。

## 12. 公开仓的内容与使用边界

这是可分发的公共源码与共享资源快照，不是维护者生产工作区的整盘镜像。包含管理台 0.8.3 源码、三个共享资源仓、通用治理入口、说明和校验清单；**不含作者平台目录、凭据、runtime、软件本体、备份或私人 Git 历史**。作者机器的成功记录只用于说明验证范围，不能作为你的平台证明。

推荐从 v0.8.3 获取固定快照，在自己的位置建立工作区和私有 Git 远端，先接入一个实际客户端，再扩展其他平台。公开上游用于获得资源和代码更新；你的本地平台配置和运行数据由自己的工作区维护。

`RELEASE.json` 记录应用号、源码来源、下载哈希和资源默认；`REPOSITORY-SHA256SUMS` 校验该发行工作树。工作区修改后自行生成新的维护记录，原发行清单不代表改后内容。

本快照的共享默认为 wf-runner 0.13.1、repo-lint 0.7.0、runtime-contracts 1.6.0、platform-conformance 1.6.2。architecture-ops 的共享 current 保留 1.5.1；工作区 `versions/anchor.json` **明确选择调用矩阵接口版 1.5.2**，供管理台的统一更新配对使用。这是声明的配对选择，不是偷偷把旧指针改成最新版。

旧公开冻结版本保留原字节；本次新加 checker 1.6.2 与复盘流程 game-retrospective 2.1.1。历史发行说明与历史校验清单保持其原版本含义，不用于认证当前新环境。
