## 1. 主要结论

慢的主要原因在 runner 的资源选择：**为选择一个工作流，反复发现全部约 1,800 个技能及它们的指针、路径。** 本轮不是首先被密封环境全量 SHA-256 拖慢；被测流程没有派发脚本、没有执行 environment_guard.verify_script。

其次，矩阵的单格过滤没有提前作用于软件询问，完整认证逐资源串行运行，无步骤进度；超时/关窗缺少整棵任务进程树的收口。普通工作区扫描与 Git 刷新有可优化开销，但它们不是几十分钟等待的主因。

仅把 full 的 30 分钟上限调大，不能解决重复扫描、单格扩大执行面和后台残留问题。仅升级到盘上的 wf-runner 0.12.0 也不能声称解决：0.12.0 的 resolution.choose 仍调用全局 discover，必须修改实现并实测。

## 2. 文件探针实测

探针均保存在文件中，避免 shell 转义影响计数。时间是本机本轮样本，不能视为所有机器的固定耗时。

| 项目 | 实测耗时 | 证据与解释 |
|---|---:|---|
| 普通 scanWorkspace | 2.201 秒 | scan-timing.json；277 次文件读取，7 次 Git 子进程 |
| 其中 Git 总耗时 | 约 1.601 秒 | 同一报告，各 Git 命令耗时相加；git status 本身 0.832 秒 |
| conform（codex 配置） | 1.875 秒 | conform-timing.json；这是正常能力读回，不是认证通过：25 pass / 5 declaredAbsent / 3 unverified |
| 单格 expert-task 资源解析，不开分析器 | **36.437 秒** | resolution-plain-timing.json；contracts 初始化 1.512 秒，choose 34.163 秒，resolve 0.763 秒 |
| 同一解析，开启 cProfile | 45.677 秒 | resolution-timing.json 与 resolution-profile.pstats；choose 42.005 秒，约占总时间 92% |
| 超时后子进程是否仍活着 | **是** | timeout-timing.json；只用本轮创建的有限时长 dummy 进程。父进程超时 1 秒后，子进程仍活着；5 秒后自然退出 |

对工作流 expert-task@1.1.0 的无分析器解析，扫描器建立了 workflow 32 / agent 15 / skill **1818** / pack 8 的全局注册表，却只检查了目标释放版 11 个文件，最后解析出 24 个资源记录。表里的 11 是此 scanner 的 checkedFiles，不能说成整个进程仅做 11 次哈希。

cProfile 归因：discover 41.997 秒；safe_path 5,742 次调用、累计 29.591 秒；read_json 1,899 次；Windows lstat 73,092 次，stat 41,130 次。累计时间有嵌套，**不能把这些数值相加**。在去掉分析器后，choose 仍占总耗时约 94%，所以结论不依赖分析器开销。

技能目录里 skills-ecc 有 1049 条、skills-nature-skills 有 379 条；所有技能目录条目合计与注册表并不要求逐条相同（停用/去重/额外资源等按原规则处理）。本轮不通过删技能减少能力面。

## 3. 现场完整认证

现场发现管理台正驱动 WorkBuddy 的完整矩阵：

- 父进程启动于 19:28:07（北京时间），脚本为 architecture-ops 1.5.0 invocation_matrix.py。
- 子进程使用 Python 3.9 和本平台自钉 wf-runner 0.10.1，读取本次 matrix-smoke 配置。
- 19:50:47 的子进程在处理 request-67；19:57:08 出现 request-77 的新子进程。期间 CPU 与请求号变化说明仍在工作，不能称为纯 UI 死锁。
- 后一次进程盘点中父进程已不在，而 request-77 子进程尚在；20:00:19 的盘点中这些进程均已结束。用户应用随后也已关闭。

**退出原因没有足够证据判定。** 源码确有 full 1800 秒上限，但本轮不能断定现场父进程一定由该上限终止，也可能随应用关闭而结束。不能把推测写成“已证明 30 分钟超时”。父退出后子进程继续这一现象，有现场记录和独立 dummy 复现两种依据。

现场本次目录在盘点时没有完整 matrix.json，也未找到 latest.json；不能依据观察到的部分请求宣布认证通过。这里只读了用户所指检查的进程元数据和报告存在性，不替 WorkBuddy 补写结论。

当前 registry 有 31 个启用且可调用工作流、15 个启用专家。以单格 choose 34.163 秒估算，46 次 prepare 的这部分就约 **26.2 分钟**，还没有算初始化、next/stop、软件询问及较重依赖。这是成本外推，不是实测完整矩阵总时长。

## 4. 定位到的代码问题

| 问题 | 定位 | 后果 |
|---|---|---|
| 每个 prepare 全局发现 | wf-runner 0.10.1 resolution.py:24、30；repo-lint 0.5.2 repo_lint.py:229 | 选一个工作流也读全部技能 current/路径；矩阵每个资源再来一次 |
| 路径校验重复 | repo_lint.py safe_path/reparse/path/base | 同一祖先反复 lstat/resolve；不能通过取消越界或链接检查来提速 |
| next/stop 再验证释放版 | wf-runner 0.10.1 engine.py:1145、1158 | 后续操作仍有真实完整性成本；本轮未分别计时，不能编造比例 |
| 单格仍询问全部软件 | architecture-ops 1.5.0 invocation_matrix.py:529–545 | software_cells 先调用全部 software，wanted_set 后过滤；未选软件也可能等待连接器 |
| 矩阵每操作新起 Python | invocation_matrix.py:237 | 每个 prepare/next/stop 都有初始化；完整矩阵放大进程启动与契约加载开销 |
| 无行级进度和取消路径 | manager src/platform-check.mjs:81–96；renderer/main.jsx:238–243 | 只显示“请等待”；输出被捕获，到最后才显示结果，用户不知道进度 |
| timeout 只管父进程 | platform-check.mjs execFileAsync；main.mjs 没有这项检查的任务生命周期收口 | Windows 子进程可以继续运行；关窗或超时后状态不清晰 |
| 完成后再全工作区扫描 | renderer/main.jsx:242 | 认证结束还要多等约 2 秒；其中多数是 Git，没有必要为刷新一条平台状态重读全部 |

software_cells 的问题由实码顺序确认；本轮没有为了测这一点向真实软件追加六次调用，因此**没有软件询问耗时读数**。next/stop、杀毒软件、磁盘介质与 CPU 降频也未单独归因，不作为已证实根因。

## 5. 建议修复顺序与 P 表

这是性能修复独立轮；初拟先做性能修复，用户随后明确改为先完成“零 AI 接入”再执行本表。实际按该顺序实施，未改变以下判据。每个 P 有三个可安全停手子块；实施前冻结目标新版本，不覆盖旧发布目录，不代各平台切生产版本。

| P | 工程时间 | 子块 | 停手产物 | 预定判据 |
|---|---:|---|---|---|
| P1 资源选择与增量索引 | 2–3 h | ① 从全局发现中分离目录注册与目标/依赖指针解析；② 按 registry/catalog/指针内容摘要缓存派生索引及重复路径检查；③ 在 staging 验证注册、停用、重复 ID、指针漂移、链接越界和依赖锁拒绝 | 候选代码、索引来源哈希、单格前后数据、负例 | expert-task 的结果与原解析一致；无关技能不反复逐目录探测；热态单格解析目标 ≤6 秒。全局 R2 保留其规则并增量复算，不用省略身份/边界校验换速度 |
| P2 单格执行范围与进度 | 2–3 h | ① wanted_set 在软件派发前应用；② harness 输出行级状态/耗时与部分维护报告；③ manager 在页面显示真实阶段/行数及独立超时信息 | harness 新版本候选、进度接口、范围读回 | 点名工作流不询问未选软件；未知 ID 和零行保持 FAIL；进度与实际调用一致，不从百分比推算成功 |
| P3 任务取消与局部刷新 | 2–3 h | ① 管理台登记自己的任务进程组并处理关闭/超时/取消；② 保留 aborted 状态与可回读部分证据；③ 检查结束只刷新目标平台，Git 按需刷新 | 有限 dummy 的进程树回读、任务记录、UI 演示 | 取消不留下本轮创建的存活子进程；不终止用户原有软件；部分报告不判完成；界面明确取消/失败原因 |
| P4 最小验证、发布与入库 | 2–3 h | ① 同一文件探针复测单格及一个有精确依赖的专家，并核必要拒绝项；② 新释放版封条、管理台双包与 README；③ 两仓提交、敏感/本体/大文件扫描、正常推送及独立远端回读 | 对比报告、新包、版本采纳指引、两仓 HEAD | 对比数据可复算；已发布字节未改；本轮目标 status 干净；旧 run 锁不静默换版；远端状态如实报告 |

P1 的 6 秒是修复验收目标，不是本次已有结果。首次全矩阵与大版本矩阵规则不变；本轮是补丁性能修复，按 BP-3 不再追加整张矩阵或逐平台重认证。缓存不能把已变化或缺失的文件当作已验证，也不能用一次客户端结果替其他平台认证。

新版本可能涉及 wf-runner/repo-lint/architecture-ops 的补丁与管理台发布，具体号段在实施前按盘上版本冻结。既有平台的生产采纳是单独的显式动作；不能只升级管理台后声称底层 runner 已获得提速。
