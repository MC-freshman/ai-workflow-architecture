## 3. 目标形状

- **域（domain）** = 一个 `agent`（人格 + policies + `tool-lock`）＋ 一条**通用 workflow**（固定骨架阶段）＋ N 个**场景（scenario）**。
- **场景（scenario）** 不是新仓、不是新品类、**也不是新的目录形态**（C-4 裁定）：它的"知识"是一个**普通 skill**——沿既有同构形态 `tool/skills/<scenario-id>/{current.json, versions/<semver>/{SKILL.md, manifest.json, SOURCE.json, SHA256SUMS}}`（实测 09-22 已有 1775 个这种释放件），索引只在所属 catalog 的 `tool/_registry/skills-*.json` 追加一行（行键 `id/version/sourceId/sourcePath/category`）；它的"形状"（阶段增 / 替 / 序、门禁、缺省值）是 **v3 定义里的 `scenarios[<id>]`**，不放独立 json、不建 `scenarios/` 子树。**不开第四仓、不在平台目录建平行功能面**（BP-1.1、1.5）。
- **`software` 侧**沿用 3.0 的形态：配方 + 冻结能力快照 + schema + 分 OS recipe + selftest + 说明书；本体/凭据不入仓（BP-1.3）。场景 skill 可以声明 `dependencies.software`，从而"场景 → 真工具"可寻址。
- **场景 ≠ 阶段图失控**：场景在 `plan()` 时**展开为确定的阶段图**，图哈希与场景名一起进 run-lock（红线 2「解析一次即冻结」；BP-4 **4.3①**（1.3 版编号：续跑版本一致性校验）的比对量靠它）。
- **目标规模**（示例口径，实际数量在 T-P1 冻结）：6 域 ×（1 专家 + 1 通用 workflow）+ 约 40 场景 skill；13 专家中 7 个标 deprecated 保留原地。

## 5. 方案划分逐条对齐上位原则（用户点名要求）

### BP-1 三仓骨架不可变
- **受约束处**：场景**不新建品类、不新建仓**，落在 `tool` 的 `skill` 品类内（1.5 的归置义务）；`software` 仍只放配方文本（1.3）。
- **推进处**：F-5 把三仓的"新增资源长什么样"写成可校验规则；F-3 保证新代字节仍满足 1.2 的四项对称（目录形态 / registry+指针+SHA256SUMS / 发布即冻结 / 可钉版可一句话切换）。
- **判据**：三仓 `switch_defaults` 行为一致演练一次（scratch 目标 + 逐字节还原）；`/versions/` 的 tracked 差集为空（**禁止就地改已发布件**）。

### BP-2 平台对等与能力地板
- **受约束处**：F-1/F-2 引入的新能力（场景展开、skill 上下文）**必须对所有平台同等可达**，不得只服务某一平台；共享件里出现平台专有路径/发行版名即违反 2.5——**场景 skill 的文本同样受此约束**（写"用 `D:\tools\xxx.exe`"就是违规）。
- **推进处**：把 `requiredProfiles` 从"零声明的空转字段"用起来（现状事实 3），使地板从名义变为实际；每域通用 workflow 声明 profile，场景不新造 profile（除非确实全新能力，那要走"补 1 条声明 + 单格冒烟"）。
- **判据**：一条 `conform` 对三仓同口径输出；**并集变化必须交前后读数**（先例：3.0 的 S-P2 一次 registry 写入把并集 25→27），新增 `declaredAbsent` 一律带补齐路径 + **整数分钟**成本（D-34 口径）。
- **边界**：qoder 只出 qoder 的结论；他平台采纳与自证各自排期（2.6），本文不代宣（§11）。

### BP-3 共享优先、验收与接入最小量
- **受约束处**：F-1…F-5 每一条都要过 §8 的三问闸门，过不了就不许进方案（含"多堆一轮验收"式表态）。**全矩阵仍只在首次平台接入与引擎/契约大版本升级两个时刻跑**（3.2⑤）。
- **推进处**：本方案的**目的本身就是把新增的摩擦压到 3.4 承诺的水平**——加场景 = 索引追加 + 单格冒烟。为此必须做 F-1/F-2，否则"每加一个场景就多发一条 workflow"，摩擦随功能数线性涨。
- **判据**：§8 的摩擦上限三条**实测读数**（不是设计意图）：新增一个场景 skill 的墙钟、改动面（应为 `0 平台文件`）、`conform` 是否一条出 digest。

### BP-4 跨平台同一项目语义（**已按 1.3 版条文重写，2026-09-22**）
- **受约束处**：4.2——进行中的 run 不热迁移；所以"12 条 workflow 合成 1 条 + 场景"**不得影响任何已存在 run 的可续跑性**（旧 run 的锁钉的是旧释放，照旧可 `status`/`stop`/续提交）。
- **推进处**：F-2 把 **scenario 名与展开图哈希写进 run-lock**，使 1.3 版 **4.3①（续跑版本一致性校验）** 有了可比对的确定量——换客户端续跑时 scenario 不符或展开图哈希不符 ⇒ 明确警告或拒绝，**不得静默换版**；另一项必需机制 **4.3②（可回读的带 sha256 交接载体）** 由 2.1 的 `handoff-bundle/v1` 承担，本文**只复用、不再设计**。
- **随 1.3 撤销的（本文同步删除一条产出）**：原 4.3③ 跨平台资源仲裁、原 4.4「并行是一等能力 + 共享编排模板」、原 4.5「中立层目录须单独授权」**已不再是必需项** ⇒ 本文**取消**"场景级并行编排模板"这条产出（它当初正是为满足 4.4 才列的），也不再声明依赖任何中立项目状态层。同域多场景**仍可**拆多 run 并行，但那是用法、不是判据；唯一被声明的互斥作用域是**平台内锁表**（3.0 参考网关）。
