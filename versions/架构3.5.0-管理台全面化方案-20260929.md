## 1. 这次要解决的问题

3.4.0 建成的管理台是一个**计划式写保护框架**（plan→confirm→apply→verify 事务内核 + 乐观锁 + checkpoint + 原子写 + 回读验证 + 审计，`src/transactions/kernel.mjs`），底座成熟且有中断/回滚测试。但按 3.4.0 方案 §4 的完整愿景逐项对照 v0.2.2 实码，它目前只覆盖了**三仓指针/registry、平台 bridge、治理文档、软件安置与受限发布**五块；作为"全面管理框架的软件"，缺口是：

| # | 缺口 | 实码证据 |
|---|---|---|
| 1 | **Git 执行器半成品**：commit/push/回滚/备份四个按钮只能出计划预览，`applyPlan` 分发表不含任何 git kind，点了没有执行器可走 | `src/git.mjs:68-95` 出计划；`src/transactions.mjs:16-24` 无 git 分支；用户面提示 `TRANSACTION_KIND_UNSUPPORTED`（`src/renderer/presenter.mjs:30`） |

## 2. "全面"的定义与目标架构

**不做重写**。在现有事务内核与模块边界（`app/api.mjs` 门面 + module-boundaries 测试锁死）上按既定接入点扩展：新 domain 模块 → query/command-api 增行 → main.mjs 增 IPC → preload 增方法 → 新 panel。管理台版本 0.2.2 → **0.3.0**，架构增量登记为本方案（3.5.0）。

管理对象全覆盖矩阵（读 = 只读盘点；写 = 必须经事务内核）：

| 管理对象 | 读 | 写 |
|---|---|---|
| 三仓资源（tool/agent/software） | 已有 | 指针切换已有；**新增发布/升级/停用向导（含 `deprecated` 标记与引用影响面）**（P4）；software 升级发布去硬编码（P5） |
| 六平台接入与检查 | 已有 | bridge 生成已有；检查证据写入已有；**新增接入向导 2.0：新平台在管理台内完成接入**（P7/P8，2026-09-29 用户补充需求） |
| 治理文档 versions/ + docs-site | 已有 | 文档计划已有；**新增 diff 视图、构建/断链检查**（P6） |
| **runs / run-lock** | **新增**（P1/P2） | 永不写（见 §5） |
| **缺陷状态簿** | **新增**（P1/P2） | **新增专用 plan kind**（P2） |
| **inbox 三区** | **新增只读盘点**（P1/P2） | 永不自动发现/执行/删除（BP-7） |
| **审计事件** | **新增**（P1/P2） | 无（内核已自动记） |
| Git/GitHub | 已有 | **新增执行器**（P3） |

## 3. 用户和部署边界（继承 3.4.0，不变）

一人一套架构副本；无中心服务器、无多人账号、无共享数据库；安装版 + 便携版双发行；源代码在独立 git 仓（**无远端是现状，如实登记，不虚构远端读数**）；UI 缓存与审计在 `%LOCALAPPDATA%\ArchitectureManager`。

**2026-09-29 用户裁定两项纳入本轮**：① 视觉层（配色/布局/主题/国际化）统一改版（§4.9）；② 支持**从 0 搭建**——他人从 GitHub 获取管理台与架构仓后，经引导向导在本机完成克隆、校验、首次扫描与平台接入（§4.8）。

## 4. 功能范围

### 4.1 运行台账（runs）面板
按平台分组展示 `runtime/runs/<run-id>/run-lock.json`：锁 schema 版本（v1.2/v1.3 及更早，未知 schema 归 `unverified` 不猜）、钉版资源行（agent/workflow/skill/pack + resolvedFrom）、执行档位（rigor/gated/frozen）、终态与阶段门禁证据链接。**登记形维护锁（agent/workflow=null）与业务 run 分色显示，前者不得呈现为可恢复业务 run**。

### 4.2 治理面板：缺陷账 + 计划中心
- 缺陷账：读 `versions/缺陷状态簿.json`，红行（open / unverified-registration）高亮置顶；登记/翻转状态走**专用 plan kind `defect-book-edit`**（目标白名单仅此一文件，附带 `缺陷状态簿.check.py` 只读联动复核）。
- 计划中心：从 `versions/` 实施表解析 P 步（编号/判据/产物路径/时长），状态由用户经文档计划维护；每步可关联 git 提交与 runtime 证据路径（只读链接，不复制第二真相）。

### 4.3 Git 执行器（收尾 3.4.0 半成品）
工作树/版本/远端/恢复四视图全部可操作：add+commit（生成提交说明）、branch/tag、push（先示远端与提交范围，**禁 `--force`**）、`revert --no-edit`、备份导出（SHA256SUMS）。全部参数数组调用、`shell:false`、动词白名单；提交前敏感扫描阻断联动；推送类操作必须当次确认。

### 4.4 三仓资源向导：tool/agent/software 的添加、更新与管理

三个动词全覆盖。**机械部分归管理台，内容创作留给用户**（要 AI 也是用户自己的选择）：

- **添加**（新资源）：registry 追加计划（catalog 面板的 add/remove/enable/disable 已有）+ 从模板生成首个 semver 目录（manifest + 定义文件骨架 + tests 占位 + 双向 `SHA256SUMS`）；
- **更新**（发新版本）：**从既有版本目录复制为升级脚手架**（预填 manifest、沿用依赖钉版，内容修改后走发布校验），或从模板全新生成；发布 = 新目录 + 双向 `SHA256SUMS` + registry 版本字段，**发布 ≠ 采纳**——指针切换是独立计划，目标必须已冻结（`assertPublishedVersion` 既有判据）；切换前展示**引用影响面**（哪些 agent 的 tool-lock、哪些 workflow 引用该资源、各平台解析来源）；
- **管理**：停用/启用已有（带现行引用保护）；**新增 `deprecated` + `supersededBy` 标记计划**（3.1.0 语义，registry 逐条编辑、不删目录、被现行引用时拒绝）；"删除"永远只产生停用/归档计划，已发布版本目录不可覆盖不可删除；
- **software 升级**：发布向导去硬编码（P5）后同一语义适用——同配方发新版本目录 + registry/current 更新；本体有变更时走既有 intake 流程（全量备份 + 恢复演练）后再发布；
- **内容边界（明写）**：workflow.yaml 的场景设计、prompt.md 与 SKILL.md 正文是**内容创作，不是管理台的活**——管理台负责"形"（目录、哈希、registry、指针、schema 机器校验如 `ai-workflow-definition/v3`），负责不了"神"；这部分内容该不该用 AI、用多少，由用户自己定。

### 4.5 软件中心收尾
启动执行器按 3.2.0 连接器语义（`software/_connector 1.0.7`）派发：执行前展示目标路径、版本、权限与预期副作用；GUI/会话型如实返回 `INTERACTIVE_REQUIRED`，不得把"窗口已弹出"写成业务调用成功；installer 保持"登记不安装"的如实声明；发布向导去硬编码（版本号、排除清单）。

### 4.6 接入向导 2.0：新平台在管理台内完成接入

> 2026-09-29 用户补充需求：接新平台时尽可能在管理台内完成，**不开维护型 AI 会话**（每次都要 AI 更新太耗费 token）。

实测依据：矩阵判据本身是机械的——`invocation_matrix.py` 以子进程直接驱动钉版 runner 的 CLI 做 prepare→next→stop（只 claim 不执行 prompt，无一步需要 AI 生成内容）；conform 同理。历史上接入烧 token 的是"维护型 AI 会话读规则、写配置、写文档、跑判据、记台账"这些**操作者工作**，全部可以由管理台承担：

- **数据驱动平台清单**：`PLATFORM_IDS` 与正式目录清单从硬编码改为"六平台基表 + 本地登记"，新 ID 零代码改动；
- **脚手架**：新平台目录、`bridge/`、`runtime/`、平台章模板，经 plan 生成——创建一级目录前双重确认，该确认即 BP-1 要求的用户授权动作本身；
- **配置骨架**：按 §9 接口表逐键表单生成 `bridge.json` + 平台 config + `capabilities.json`（含 `declaredAbsent` 预登记），明文密钥拒绝规则沿用；
- **一键流水线**：静态预检 → conform → 矩阵串行执行，失败格子逐格重跑，证据归档该平台 `runtime/`（沿用 manager-check 登记形态）；
- **真实提交一格（唯一 AI 环节）**：管理台生成指令卡"在新平台里执行 `/wf <id> <任务>`"，用户粘贴执行；管理台读回 run-lock 与终态核验并归档。这一格不可自动化——"该平台的 AI 能不能真实干活"本身就是被认证对象；不得为省它而把"机械矩阵通过"写成"完整接入"；
- **治理文档联动**：`AGENTS.md` / `AI_ARCHITECTURE_SYSTEM_PROMPT.md` / `HANDOFF.md` / 平台接入清单 / 更新日志的增补走文档计划（顶层文件保留高敏感确认）；
- **收口一键化**：维护台账脚手架 + BP-6 四项读数。

### 4.7 首页聚合与文档中心
首页新增读数：缺陷红行数、最近失败、`declaredAbsent`/`unverified`、runs 汇总、inbox 计数。文档中心新增 git diff 视图与 docs-site 构建/断链检查（作为命令型操作，只写 `docs-site/build`，不碰发布目录）。

### 4.8 工作区引导向导：从 0 搭建自己的架构（2026-09-29 用户裁定新增）

目标：**其他人从 GitHub 拿到管理台后，能方便地搭起自己的架构**。首次启动欢迎页给两条路：

- **克隆搭建（推荐主路径）**：输入架构仓远端（现行 governance 仓，含三仓全部已发布版本）→ clone 到用户选择的本机根（参数数组调用 git、进度反馈、失败清理半成品）→ 完整性校验（远端 HEAD + 仓内逐版本 `SHA256SUMS` 抽验）→ 选为工作区 → 首次只读扫描 → 进入平台接入向导（§4.6）。新用户完整旅程：**装管理台 EXE → 克隆架构仓 → 接入自己的平台 → 开工**，全程不进命令行；
- **打开已有工作区**：现有行为不变（`E:\ai` 等既有架构只能打开，**不得**在其内再生成骨架）；
- **空白骨架（仅开发/测试）**：生成三仓空 registry + versions 治理文档模板 + inbox 三区；界面明写"无引擎种子，不能跑业务 run"，不作为用户主路径；
- **分发配合**：README 快速开始（下载 EXE → 引导 → 接入）；管理台源仓绑定远端与发布走 Git 面板（P3 执行器），push 由用户当次确认。

## 5. 数据归属与安全边界（新增领域的裁定）

- **管理台不是第七个平台**：runs/inbox/缺陷账面板是用户对本机自有数据的**只读盘点**；管理台不写任何平台 `runtime/`，唯一例外沿用现例——显式归属平台的维护证据目录（时间戳子目录、登记形态、不冒充业务 run）。
- **不做跨平台 run 操作**：热迁移、续跑、交接仍按 BP-4 由平台会话经 `handoff-bundle/v1` 执行；管理台只展示哈希与摘要，不 become 交接通道。
- **凭据零经手**：GitHub 凭据走 Git Credential Manager；管理台不读出、不落盘、不进 plan 与审计正文（内核现状已满足，新增领域沿用）。
- **inbox 红线**：盘点≠发现≠执行≠删除；三区面板无任何删除按钮。
- **不建第二真相**：所有新面板读原始文件（run-lock、缺陷簿、events.jsonl、git），不复制快照进应用数据目录。

## 6. 与现有架构的关系（继承 3.4.0 §6 全部八条，另加六条）

9. 管理台对 runs/缺陷/inbox 的扩展**不新增任何验收门**：不向 conform 增行、不向三仓 registry 增资源、不给平台添 `declaredAbsent` 项（BP-3：这是用户工具，不是平台能力面）。
10. `defect-book-edit` 与发布向导是**新的 plan kind**，全部走既有事务内核（乐观锁/checkpoint/原子写/回读/审计），不另造写路径。
11. 管理台自身演进的账记在**根仓治理文档 + 管理台独立仓**两处，两仓收口各自出 BP-6 四项读数。
12. 管理台驱动矩阵/conform **不改变 BP-2 的自证语义**：证据产自该平台自己的 config 与自己的 runs，管理台只是操作者；接入完成的权威判据仍是"矩阵 FAIL 0 + 能力并集 0 `declaredAbsent`"两个读数，不由管理台 UI 声明，历史台账上的"各平台自证、结论不互抄"口径不变。
13. **接入自动化的 AI 下限**：矩阵判据机械（claim+stop，不执行 prompt）；唯一不可自动化的是至少一格真实提交闭环，必须在新平台的 AI 会话里执行，管理台只生成指令与读回核验。判据口径照旧：首接跑一次全矩阵（BP-3 的两个合法时刻之一）。
14. 引导向导在**用户新选的根**下搭建正式一级目录集＝该新工作区的初始化，属用户当次显式授权（双重确认）；对 `E:\ai` 本身不适用——已有工作区只能打开，不能在其内重建骨架。

| P | 时长 | 子块（按顺序） | 安全停手产物 | 通过判据 |
|---|---:|---|---|---|
