## 2. 三仓同构（BP-1 的 3.0 判据）与四条裁定

`software/registry.json` 与 `tool`/`agent` 的 registry 同构，指针七轴在 `software/registry.json` 的 `compatibility.axes` 里逐条写明。**执行期裁定（不得再出现"两种形态都对"）**：

- **选择键只有一个：`version`**。软件仓原用 `current` 作键名的形态自 S-P2 起废除；`updatedAt` **废除**；`available` 降级为"`versions/` 目录枚举的缓存"且必须相等；`hashManifest` 必填。
- **`_gateway` 不是配方**：它有 `versions/1.0.0/` + `SHA256SUMS` + `SOURCE.json` + 自己的 `current.json`（复用 `ai-software-pointer/v1`），但**不进 `software/registry.json`**——registry 列的是"可被调用的软件"，网关是共享程序件（同 `repo-lint`/`wf-runner` 的关系）。平台用 `config.softwareGateway` 指向释放版字节，run-lock 记其 sha256。
- **`switch_defaults` 三仓一张表**：`SECTIONS`/`ROOT_KEYS` 各三键（`toolRoot`/`agentRoot`/`softwareRoot`），plan→apply(CAS+checkpoint)→verify→revert 与"绝不改共享 `current.json`、绝不跨平台"两条闸语义完全一致（S-P2 演练、S-P8 复演）。
- **改 registry / manifest 必须交并集前后读数**：写 `software/registry.json` 立刻改变已发布 `conform` 的能力地板（实测 **25 → 27 项**，软件仓的两个 `profile:` 进入地板），所以每一步都要重算并集并补本平台 `gapPlan`（整数分钟）。本轮发布后复算：并集未移动（§11 S9c-03）。

## 3. 软件面契约（`ai-software/v1`）与 C-1…C-6 的落地形状

- **`invocation` 是 `cli-wrapper` 的必填能力项字段**（C-1），键名与类型按**实盘六份已发布配方**写进新 schema ⇒ 判据反过来约束 schema：**六份旧配方逐字不变即过新校验**（S-P3a 硬判据，旧资源零回归）。
- **缺 OS 配方不拒发布，但必须报登记级 finding `SOFTWARE_RECIPE_MISSING`**（每 OS 一条）且该平台 `conform` 把它判为 `declaredAbsent`（C-2）；`supported` + 无配方**不得**被读成"可用"。
- **`requiredProfiles` 是不透明 profile 键的字符串数组**（C-3，1–16 项，不加版本语法）；版本约束归 recipe 的 `interpreter`。实盘的 `python>=3.8` 作为**字面键**保留（不回改已发布配方）。
- **凭据只允许 `none` 或 `reference:<name>`**（C-6），由 schema pattern 直接拒其他值 ⇒ 仓库、run-lock、证据三处只可能出现引用名。明文脱敏的深水区维持 §7.4 的 openDeferred（§10）。
- **`SOFTWARE_DRIFT` 的比对基线＝冻结快照**（C-4）：快照缺失或 `frozen: false` ⇒ 引擎/网关报结构化 `CAPABILITY_UNAVAILABLE` 并点名配方字段，**既不静默放过、也不误报成漂移**。实测后果：**六个生产配方快照全部未冻结**（D-47），因此本轮软件面矩阵行 6/6 是 `EXPECTED/SNAPSHOT_NOT_FROZEN`，没有一个绿行；而 `frozen: true` 只能靠**发布新配方版本**做到（不回改已发布件）。

## 4. 引擎 `software-call`（§6.1–6.3 的落地）

**八步固定链，顺序可机判，失败一律发生在派发之前**：

```
declared → snapshot → profile → boundary → consent → arguments → idempotency → dispatch
```

每一步在 `evidence/gate-chain/<stage>-<attempt>.json` 留一条 trail（含被拒那一步），每步一个负例（S-P5 电池 8 格）。派发面：

- **幂等与重放**：引擎算 `sha256(stageId|attempt|capability|argumentsSha256)`；派发前以独占写落 `software-intents/<stage>-<attempt>.json` 锚点，网关在 `evidence/software-calls/<seq>/request.json` 落重放锚；同一 `software-call` 重跑 `--execute` 答 `replayed: true`，**不重复派发**（S5b 实测）。
- **证据三件套**：`request.json` / `response.json` / run 台账 `reports/software-calls.json`，并以 `software-called` 事件（`ai-run-event/v1.2`）把两份证据字节绑进事件流。
- **确认门不是 `gates[]` 项**（C-7）：`gates` 复用既有五种通用门禁类型作用于调用输出，确认门是链上独立一步，避免同一件事两处触发；`consent` 授予以 `softwareConsentGrants` 声明并绑定**精确请求摘要**（"批准 ffmpeg"不会膨胀成"批准一切"）。
- **软件调用不做 onFail 修复**（编译期直接拒），也不支持 run 中途补同意——两者都写进发布件的 `SOURCE.openDeferred`（§10）。
- **无密封环境时不封顶功能**（BP-2 的口径在 3.0 的延伸）：`software-call` 的判定不依赖脚本环境；本平台脚本环境灭失后，`prepare/next/stop` 与提示词面照常，脚本派发 fail-closed 报 `HASH_MISMATCH`（2026-09-21 实测读数，见台账 §7）。

## 5. 网关、并发与独立性（§10 的实测行）

三级模型：**仓库级**只读共享配方、本体各平台自装；**run 级**独立网关会话与独立证据目录（默认可并行）；**实例级**由配方 `concurrency` 决定（`per-run` / `pooled`（并行度＝`poolSize`）/ `singleton` / `exclusiveResources` 加锁）。机读必填 + README 人读章节缺一不可（S-P3a 校验）。

本轮 run 级实测（S-P8 子块 3，全部在独立 scratch `runsRoot` 与 mock 软件上）：

| 用例 | 判据 | 实测读数 |
|---|---|---|
| **C6** | `per-run` 软件、两 run、各自项目副本 ⇒ 都成功且证据互不串 | 两 run 的 body 区间**实测重叠**（两个 pid；合体窗口 3.26 s，串行应为 6.4 s；阈值 1.3×hold）；两棵树各自 `request.json`+`response.json`；`outputSha256` 两个不同值；四个项目副本各只含自己那一个文件 |
| **C7a** | 同一项目副本被第二个 live run 抢占 ⇒ 拒，且**被拒者零落盘** | prepare 即 `RESOURCE_BUSY`；被拒 run 目录**根本没创建**（不是"创建了但没提交"）；持有者状态一字未动 |
| **C7b** | `singleton` 软件两 run 同刻派发 ⇒ 一串行一 BUSY，状态不损坏 | 被拒方 `SOFTWARE_BUSY`(`retryable: true`) 且**从未进入 body**（marker 日志只多一家）；被拒方无 `evidence/software-calls`、无台账行、`stateRevision` 未变、 contested 项目副本字节不变；holder 停止后新 run 正常取得实例，被拒 run 仍能干净 `stop` |

跨平台仲裁**未满足**并按 BP-4 原文登记（C-8）：锁表目录仍是本平台 `runtime` 内一件，`capabilities.json` 的软件面明写 `lockTableScope: platform-internal`、`crossPlatformArbitration: NOT satisfied`。

**〔2026-09-22 裁定更正，原文保留〕** 用户裁决把 BP-4 的必需机制由三项裁减为两项，**跨平台资源仲裁不再是必需项**（`versions/架构基本原则.md` BP-4 1.3 / 清单 §8.20）。因此上面那句"未满足"自今日起**读作作用域声明、不读作缺口**：锁表只在平台内即为正确形态。`capabilities.json` 里 `crossPlatformArbitration: NOT satisfied` 的**机判措辞本轮未改**——那是配置面，改动须随本平台下一轮自证重新出证（`declaredAbsent` 一栏会随之少一项要求，而不是多一项修复）。**被接受的代价明写**：同一项目副本被两个客户端同时开工时不会被任何机制发现或阻止，两边会互相覆盖。

## 6. 一句话切换、闭包与回滚（§9 的落地形状）

成对切换闭包在 S-P8 落成**一条可复算规则**（写在 `baseline/s8-pair.json` 的 `closureRule`）：一个切换批次合法 ⇔ 批次内每个目标释放版存在且双向完整、其 manifest 的每条依赖 pin 被批次或现有指针满足、其 `SOURCE.pairingRequired` 的每个同伴都在批次内、且任何同时命名版本的 registry 行与指针一致。三种拒绝各有实盘：

1. 只切引擎 ⇒ `PAIRING_NOT_IN_CLOSURE`；
2. 六件指针全切但引擎 manifest 仍钉旧 scanner ⇒ `DEPENDENCY_NOT_IN_CLOSURE` + `STAGED_PIN_NOT_REMEDIATED`（**这就是 D-49 以"块"的形态被测出**）；
3. 只翻 agent 指针不翻 registry 的 `version` 字段 ⇒ `REGISTRY_POINTER_DISAGREEMENT`（D-36）。

三次拒绝全部**零字节写入**（整树哈希图复算）。逐字节回滚演练（BP-3 §3.4 的"每引擎大版本一次"，本轮即那一次）：批次碰过的每个文件先落 checkpoint 原件，revert 后三仓镜像整树与 `pre-drill-map.json` **逐字节等值**，且非空洞性对照（给副本加一个空格即被同一套双向完整性 routine 抓到）。三仓各一次完整 cycle 打在 3.0 代字节上，`sha256Ledger` 每仓留五把哈希（before / applied / after-revert / backup / plan），revert 后与生产 bridge 字节同一。

**共享侧仍无带 checkpoint 翻 `current.json` 的工具**（D-31 未修）；本轮的"同切同回"由该子块内的 scratch 驱动器证明，不冒充共享能力。

## 7. 本平台接入面（八项接口中 3.0 新增的部分）

- 三根接线：`toolRoot`/`agentRoot`/`softwareRoot` **同一套只读绑定**，jail 内三根可见且写入全部被内核拒（`errno 30 EROFS`），`/work` 仍可写（S-P7 在本平台控制器上实测，非推定）。
- 本平台按 recipe 取用真本体：`qoder/runtime/software/software-environment.json` 登记六件本体的检出路径与逐文件哈希比对（`mysql-cli`、`wireshark-cli` 走配方自带只读 selftest 出报告），**没有把任何本体复制进运行时或共享仓**；需要许可/需要人工的格按 §4.2 出 **EXPECTED 不出 FAIL**。
- 声明面：`qoder/bridge/capabilities.json` 的 `descriptor.software` 记网关节要、`lockTableScope`、`bodiesPresent`、`snapshotFrozen: []`；`action:software-call` 进 `declaredAbsent`，理由写的是**未采纳**而不是不可能，并带 `costMinutes: 20` 的采纳路径；快照冻结（45 分钟）与生产 `softwareRoot` 声明（15 分钟）各自带路径与整数成本。
- 软件缺口进本平台裁决台账：`qoder/bridge/invocation-exceptions.json` 的 `pendingGaps` 现有六条 `software:<id>@*`，每条带 `expectedCode`、补齐路径与整数分钟成本。

## 8. 完成判定（这张表跑完＝什么完成了）
