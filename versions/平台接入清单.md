# 平台接入清单（对照架构 1.0.0）

> 适用版本：**架构 1.0.0**（2026-09-15 定稿；平台状态更新至 2026-09-16）·　配套文档：`versions/架构1.0.0.md`、`versions/架构1.0.0-接入状态-20260916.md`、`invocation-adapters-spec.md` §9
>
> **前提**：共享侧（`tool` + `agent` 仓库、引擎、接口契约）已就绪并实测通过。**"接入"是每个平台自己的动作**——按平台隔离规则，任何平台不得替另一个平台改配置、状态或工作区。本清单是给各平台会话照着做的步骤，不含任何跨平台改动。

---

## 0. 一句话判据

**接口面接入完成的机械判据是：本平台配置下 `invocation_matrix.py` 跑出来 FAIL 0。** 在此之前都不算接入。FAIL 0 证明 prepare→next→stop 可调用，**不等于**脚本阶段、peer、MCP 或数模交稿可用；那些以该平台 `capabilities.json` 为准。矩阵必须显式传入本平台 `--config` 与 `--exceptions`。

**能力面接入完成的判据（BP-2 conformance floor，2026-09-18 加入）：对共享侧从 `tool`/`agent`/`software` 三仓 registry 集中算出的能力并集，本平台 0 个 `declaredAbsent`。** 只达到 FAIL 0 而仍有 `declaredAbsent` 的平台，处于"接口已通、能力面未完成"状态，须列**待补台账**（带补齐路径与成本），**不得**表述为永久分层或"本平台不支持"。

**成本口径（BP-3）：整张矩阵是"首次接入本平台"与"引擎/契约大版本升级"的一次性成本。之后新增或升级单个 tool / agent / software 配方，一律只做增量索引 + `--only <id>` 单格冒烟，不得重跑全矩阵、不得逐平台重认证、不得每发布做逐字节回滚演练（后者每引擎大版本一次）。未变能力按内容哈希沿用既有 attestation。** 新增任何验收动作前先过三问：抓的是不是真失败？能不能增量？能不能并进同一条 `conform` 命令？三问不过不得写进方案。

## 1. 八步接入清单

| # | 步骤 | 要做的事 | 判据 |
|---|---|---|---|
| 1 | 写平台配置 | 一份配置 JSON：`platform` / `platformRoot` / `toolRoot` / `agentRoot` / `runsRoot`（共享仓库**只读**，运行产物只落本平台运行根） | 路径全部指向本平台目录 |
| 2 | 选引擎版本 | `runner` 指向一个**已发布**的引擎版本目录 | 目录内 `manifest.json` + `SHA256SUMS` 齐备 |
| 3 | 对齐契约钉版 | `contracts` 指向与共享默认一致的契约包版本（当前为 `repo-lint 0.2.1`） | 解析时不报 `Runner contract dependency conflicts` |
| 4 | 能力自证 | `capabilities.checks` 全为真（隔离验收已通过） | 引擎在 prepare 时校验；有一项为假即 `Isolation acceptance has not passed` |
| 5 | **声明 profiles** | `capabilities.profiles`：列出本平台能兑现的 profile 及其所需包 | 未声明的 profile 一律被拒（这是设计，不是缺陷） |
| 6 | **声明权限适配器** | `capabilities.permissionAdapters`：逐条列出**已验证的权限策略三元组** | ⚠️ **不声明则 0.6.0 下每次调用都被拒**（`Required permission policy has no verified adapter`） |
| 7 | 脚本 / 派发（按需） | 要用脚本阶段：`scriptEnvironment` + `environmentManifest`（逐文件清单）；要用 peer 派发：`peerDispatch` + 派发器模块 | 脚本阶段报 `Actual script environment inventory is required` 即未配好 |
| 8 | 验收 | 跑 `python -B ops/invocation_matrix.py --out <报告>` | **FAIL 0**；非 PASS 项须逐条解释 |

## 2. 顺序要求（**别搞反**）

**先声明能力（第 4–6 步），再切引擎（第 2 步）。**

理由：0.6.0 把"哪些 profile 可满足""哪些权限策略已验证"变成了平台**声明**。若平台没声明就换引擎，结果是**每一次调用都被拒**——不是变慢，是完全不可用。

历史上的 `codex` 曾是反例：只有 `checks`、没有 `profiles` 与 `permissionAdapters` 时，不能直接从 `0.5.2` 跳到 `0.6.0`。Codex 已于 2026-09-15 按正确顺序补齐声明后完成升级；这条历史仍说明了为何必须先声明能力、再切引擎。

## 3. 能力声明的最小示例

```json
{
  "checks": { "python-runtime": true, "...": true },

  "profiles": {
    "renderer": {
      "adapters": ["matplotlib-adapter-first"],
      "requires": ["matplotlib"]
    }
  },

  "permissionAdapters": [
    {
      "filesystem": "project-scoped",
      "network": "deny",
      "process": "allowlisted-only",
      "evidence": "本平台自证：<验收依据>（<日期>）"
    }
  ]
}
```

要点：

- `profiles` 的键是 profile 名，`adapters` 是平台愿意兑现的适配器标识，`requires` 是**必须已钉版**的包名。
- `permissionAdapters` 每条是一个**精确三元组**；引擎要求与工作流声明的策略**完全相等**——不放宽、不做子集匹配。
- **只声明真正验证过的**。没验证过的策略不要写进去（写了等于谎报隔离能力）。
- `evidence` 字段会被引擎忽略（比对时剔除），但它是对人交代的依据，建议写清来源与日期。

## 5. 接入后必然要回答的一个问题：例外清单

跑完矩阵后，非 PASS 项通常来自两类，**都要如实登记，不要掩盖**：

- **设计如此**：`wf-runner` 是引擎自身，自调用成环，不作为用户可调用工作流 —— 所有平台都一样。
- **平台能力缺口**：例如 `repo-lint` 声明 `filesystem=shared-read-only-platform-report-write`，需要**只读访问共享仓库**。这取决于该平台的脚本隔离模型：
  - 若隔离只提供 copy-in 工作目录，或像 2026-09-17 后的 zcode 一样**没有脚本环境** → 该平台同样调不动 `repo-lint`；
  - 若隔离允许只读挂载共享根 → 该平台可声明该策略并真正跑通。

**每个平台都要自己跑矩阵才知道自己这边的例外是哪几条**，不要照抄 zcode 的结论。

## 6. 不要做的事

- 不要为了让矩阵变绿而**放宽判定**（例如把没验证的权限策略写进 `permissionAdapters`、或把 FAIL 直接记成 EXPECTED）。
- 不要**跨平台改动**（改别的平台的配置、状态或工作区）。
- 不要**覆盖已发布版本**；新版本一律新建目录，通过 `current.json` 切换。
- 不要跳过第 8 步的矩阵验收；没有 FAIL 0 就不算接入完成。
- **（BP-2）不要写平台分层**：不得用"主平台 / 高完整度平台 / 本平台不支持"来固化差异；未完成就写"待补 + 补齐路径"。作者、搭建者、定稿会话的身份不产生任何运行时特权。
- **（BP-2）不要把"只接了 `tool`+`agent` 两根内容根"当作设计如此**：`software` 是三仓的对称成员，缺 `softwareRoot` / 缺 jail 内 `/shared/software` 属接入未完成。
- **（BP-3）不要因为"顺手"而重跑全矩阵**：新增单个资源却跑整张 39 格、或对未变能力重新认证，都是违反最小量原则的返工。
- **（BP-4）不要用直读别平台 `runtime/` 的方式实现"跨平台续跑"**：唯一被许可的跨平台状态通道是平台中立的交接包/项目层；单平台内的 `projectWriteRoots` 互斥或网关锁表不构成跨平台仲裁。
