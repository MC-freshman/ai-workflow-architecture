## 3. 要改变的产品行为

### 引导说明

- 先确定用户首次要完成的真实任务；在首次进入或空状态给一个可行动入口、必要输入说明和适用的真实示例。
- 复杂操作按步骤展开，向导可跳过、可从帮助入口重新打开，尊重已经关闭的提示；简单控件不堆解释。
- 按钮写明动作与对象；输入要求在提交前可见；失败提示说明发生了什么、可以怎样恢复，技术错误码放详情。
- 交付快速开始：如何启动、首次任务、输入示例、预期结果及结果位置、常见错误和恢复。CLI 软件用 `--help`、命令示例与退出错误说明表达，不强加图形界面。
- 用户只点名小修时，仅补本次涉及的说明；不把“引导更完整”变成每次追加完整手册。

### 界面风格

- 按产品用途、实际使用设备、受众、已有品牌和用户风格确定视觉方向，再选择字体、颜色、信息密度和布局；不预设网页、React、深色或营销首页。
- 为新界面或较大界面任务记录短设计说明及可复用 token；小改直接使用已有规则，避免重复建设设计系统。
- 明确标题/正文/辅助文字层级，统一间距、组件和图标规则，状态颜色有固定含义；中文字体与实际长文案必须适配。
- 用真正渲染的页面或应用检查溢出、对齐、对比度、键盘焦点和完整状态；美观判断须对照已选方向并附实际截图，不能用“检测没有报错”代替视觉复核。

### 领域分工与上下文

`software-engineer` 负责软件逻辑及体验交付要求，检测界面/引导是否有落实产物；`frontend-engineer` 负责界面实现；`ui-ux-designer` 负责视觉与交互契约。每项具体任务仍有一个领域负责人，不把三个专家的常驻核心拼成一个全能提示词。

本表不新增自动多专家派发链、不修改引擎或平台委派配置，也不声称仅加入技能就获得原生多模型协作。需要相邻专家的任务给不超过既有 2,000 估算 token 的摘要与产物索引；未实际完成的界面工作明确留待办。

每位专家仍然 **一份常驻领域核心 + 一条主 workflow + 按场景选择的辅助卡**。软件默认场景只加短体验路由；完整视觉方法放在前端/设计场景中；后端、缺陷小修、CLI 不无条件加载全部 UI 卡。保留现有预算：常驻核心 ≤2,500，选中辅助合计 ≤4,000，常规固定载荷 ≤8,000，绝对上限 ≤12,000 估算 token；深度读取每批 ≤4,000。新辅助卡每张入口目标 ≤900，体验路由入口 ≤800。以上是固定载荷估算，不等于模型完整会话窗口实测。

## 6. 发布、回滚与完成口径

先在 Codex staging 完成 P2/P3，再按 P4 生成新版本目录；旧版只读。修改面是 §4 的资源、对应 current/索引和本次治理文档；software 仓、现有平台配置、业务项目、管理台源码及原生模型连接不在范围。Codex 当前三个专家没有本地版本覆盖，共享指针变化可在新 run 中读取；其他平台是否有覆盖由各自会话核对，不跨平台改配置。

P1 的可回滚 commit、指针/索引逐文件字节快照与本次变更路径构成恢复载体。失败时恢复本次指针/索引，不删除旧版、不覆盖在途 run 的精确锁；新发布目录保留为候选/诊断证据，已启动探针显式停止。

完成只按本表判据判断，不追加“所有软件都必须达到某审美”“真实新人成功率已证明”或其他平台完整接入等条件。执行期新发现的非阻断缺陷登记现象、复现、影响、定位、建议，不顺手修改。

收口必须写明 18 件实际发布/切换、预算读数、样例的检查结果与限制、一级目录未新增，以及 BP-6 四项实际 Git 读数。没有实际截图/运行就不得写界面已检查；没有业务交稿就不得称已冻结。本表的维护样例证明具体方法和链路可用，不承诺所有未来软件的审美或新用户成功率。
