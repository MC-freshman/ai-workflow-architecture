# 架构管理台：接入过程不需要 AI 的改造方案与 P 表

> 日期：2026-09-30。状态：**用户已批准，实施中**；原核对基线为 0.3.1，实际进度见 [3.6.0 执行记录](架构3.6.0-执行记录-20260930.md)。以下技术范围和 P 判据保持批准时口径。
> 建议登记为架构 3.6.0、管理台 0.4.0；号段在执行前核对，不预先宣布发布。
> 来源：用户要求“平台通过管理平台接入后就不需要 AI 跑接入”。
> 基线：根仓 f1698879；管理台源仓 d63b949；package.json 为 0.3.1。
> 本次是源码核对与方案维护，agent/workflow = null，未执行业务工作流。

## 1. 可以做到什么

**可以让用户通过图形界面完成接入，不开维护型 AI 会话，不手写 JSON，不使用控制台。** 管理台负责配置、安装准备、注册入口、检查、证据、治理登记和回滚。业务任务是否使用 AI 取决于业务本身，不由接入向导改变。

“一键”指用户选好工作区、客户端和必要位置，查看变更清单并确认后，管理台连续执行可自动化步骤。首次登录、操作系统提权、系统组件安装后的重启、软件许可确认仍通过它们自己的界面完成；管理台暂停并在恢复后继续，用户不用找 AI 补文件。

**不能承诺任意未适配客户端立即一键接入。** 新客户端需要有已实现并验证的适配器。标准 CLI/MCP 客户端可以复用通用适配；没有可编程入口的客户端，需要一次性开发客户端扩展或保留一次用户点击“测试连接”。这是适配工作的时间差，界面应显示待适配及补齐路径，不能生成目录后宣布完成。

本方案把“接入成功”的验证对象限定为配置、环境和调用通路。接入认证不宣称某个模型的业务输出质量已经通过测试。

## 3. 用户怎么用

1. 打开管理台，首次选择自己的架构目录；以后记住最近工作区，也允许切换。
2. 点击“接入平台”，选择已支持的客户端类型。已有目录走修复/升级，新平台填写 ID 与显示名称。
3. 选择客户端位置或连接地址。向导检测本机解释器、运行环境、软件位置；大多数值自动填写，缺项显示“选择位置”或“安装所需组件”。
4. 查看一页变更摘要：目标平台、版本组合、安装位置、需要空间、配置差异、系统权限和回滚点。创建新一级目录时明确确认授权。
5. 点击“开始接入”。界面显示配置→环境→入口→检查→登记进度；失败停在该步骤，并提供白话原因、修复按钮及“继续”。
6. 完成后看到真实读数、配置/证据位置、当前使用版本；能查看变更、修复接入或撤销本轮变更。

界面状态依次是：未配置、待准备环境、待注册入口、正在验证、待用户操作、接入完成、接入失败。仅生成文件不能进入“接入完成”。“排除视图”继续只管理可见性；另设“停用接入”计划，说明会暂停哪些入口，不直接删除目录。

## 4. 用什么做、怎么做

### 4.1 继续使用现有软件底座

使用已有 Electron 主进程、React 界面、IPC/preload、Node 子进程 API 与 transactions/kernel。无需改成中心网站，也不新增架构共享仓。每个用户管理自己的本机架构。

新增接入领域模块：onboarding-model（状态与证据引用）、onboarding-plan（配置与变更）、onboarding-executor（执行/中断/恢复）、client-adapters（客户端接线）、runtime-provision（按配方准备环境）。模块名称是建议，依赖边界沿用 app/api 与 core，最终字段在 P1 固定。

子进程用 executable + 参数数组，shell:false。管理台的启动与校验程序使用明确选择并探测过的解释器，取消隐式 PATH python。未知命令不根据错误字符串临时拼装执行。

### 4.2 一套平台目录解析规则

core/platforms 提供唯一的“读取已登记平台”接口，扫描、选择器、软件中心、接入检查和事务验证全部使用它。六个既有平台作为兼容起点；新 ID 从用户确认的登记与合法 bridge 发现，不靠复制六 ID 白名单。

发现 bridge 只代表发现对象。需核对 schema、platform ID、所属工作区、真实路径、符号链接/目录联接越界和配置文件所属平台，才能进入操作列表。inbox 与三仓不作为平台发现范围。

### 4.3 版本与配置自动生成

读取当前三仓指针与 manifest 依赖，生成相容的 runner/contracts/scanner 组合；不把三个 current 的独立读数盲目拼成一套。记录具体版本与 SHA256SUMS，应用前重验，续跑不静默换代。

bridge、runner config、capabilities、软件连接器配置与客户端入口形成一份有基线哈希的计划。runner config 的逐键表单覆盖环境、解释器、软件、委派和权限；简单模式自动填值，高级模式显示字段来历和实际路径。正式配置中不留下 PIN。

能力声明由“可复算配置 + 对应实测证据”共同产生。用户不能通过勾选“已支持”消掉缺口。capabilities 保留已有有效声明和证据引用，新增声明只覆盖本轮真实探测到的项目。

### 4.4 环境准备也是向导职责

环境选择 BP-1 的第三条归属路：**所属平台 runtime 内独立准备**。解释器、库、密封环境、软件状态分别登记，不能借用另一平台的 runtime 或 venv。

运行环境优先复用本机已可验证的系统设施，并从三仓 manifest/profile 与已冻结的环境配方计算需求。缺 Python 时提示选择已有解释器或按有来源及哈希的安装描述安装；需要密封环境时使用现有 runner backend 与 environment_verify 机制，不以普通 Windows 进程冒充密封沙箱。

若需要 WSL/系统功能，向导展示系统变更、所需下载与重启，由用户确认，再由有能力的 provider 执行；不能默认安装一个带特定发行版名的共享特例。已登记配方不足的需求进入明确缺口，不能凭 AI 临时编造安装命令。

安装先落 staging，校验后激活；中断可重入。备份落 inbox/backup/<platform>，保留重建配方、逐文件哈希及重建命令，并做一次隔离恢复验证。安装等待不占用 AI token。

### 4.5 软件、权限和委派按原接口接线

软件继续使用 software/_connector 和平台 provider，不另写一套软件派发器。用户选本体位置后验证版本/快照匹配，必要时走现有安置/备份流程；凭据只登记引用，使用既有凭据 provider。

GUI、管理员权限和外网请求按精确请求保留原确认要求；接入确认不授予永久提权，也不能代替后续扫描等业务的逐次授权。管理员能力只验证当次 consent provider 可工作。

peerDispatcherModule、peerContentRoot 和能力位成组填写并真实探测；不能把存在一个 Python 文件当作平台具备真实委派能力。

### 4.6 客户端适配器：解决“管理台代跑”的问题

适配器需要提供检测客户端、生成安装计划、读取/合并原配置、注册入口、探测连接、执行工具回环测试、撤销本轮配置这些操作。核心按能力与传输选择适配器；厂商差异仅存在客户端适配器，不能进入共享引擎或软件配方。

第一版提供可配置 CLI 与 MCP 两种接线方式，既有客户端按实际接口登记预设。新增厂商配置形态需要一次开发适配器；用户以后只用图形界面选它。

**MCP 服务端握手成功不等于原生客户端已使用它。** 客户端验证要有来自客户端或其扩展的回执：管理台发送随机 challenge，客户端登记的入口调用只读探针，返回相同 challenge、platform ID、配置摘要和钉版摘要。完整链路实际经过客户端入口，不允许管理台绕过客户端直接调 runner 却声明原生入口成功。

客户端有自动化/扩展 API 时自动完成；只有界面测试入口时引导用户点击一次；完全没有相应接口时显示“运行环境已准备，客户端入口待适配”。上述两种成功路径都不要求 AI 生成回复或输出业务结论。

工具回环是维护探针，不构造假的业务 submit，不把 fixture 结果写成真实业务成功。正常业务的 prompt/delegate 等阶段仍由业务执行器完成。

### 4.7 可恢复的执行流水线

按顺序执行：静态预检→准备缺失项→写入配置与注册入口→真实能力探针→conform→首次全矩阵→客户端工具回环→治理登记→Git 收口。所有异步步骤 await，统一用结构化 status 与读数判断是否继续。

首次接入按 BP-3 跑一次全矩阵。配置未变的有效证据可增量沿用；失败只补对应能力并重跑受影响格，不能把上次缓存显示成刚执行的检查。任何 await、超时、进程退出、空报告和配置漂移都需要明确反馈。

持久状态是平台 runtime/maintenance 下的登记形记录，含执行步骤、目标配置/证据哈希和恢复点，不是第二份可编辑的平台真相。恢复时从原文件重验；仅 UI 本机工作区偏好写应用数据目录。

每个写步骤走计划、基线锁、checkpoint、原子写、回读和审计。跨文件操作是可恢复的多步事务，不声称一个 rename 能让所有文件全局原子提交。撤销仅恢复本轮未被他人再次修改的文件；发现新改动就暂停展示差异。

## 5. 需要修订的旧规则

3.5.0 方案 §4.6 与 §6.13 规定“真实提交一格必须由平台 AI 会话执行”。按用户本次需求，新的方案采用客户端工具回环检查；在实施轮中同步修订这些条款及平台章模板，保留旧轮实际证据，不将它们回写为新判据通过。

这次修订不降低 BP-2：证据仍来自目标平台自己的配置、运行环境和客户端入口；不得复制其他平台结论。保留矩阵 FAIL 0 与 conform.floorReached。现实现中 floorReached 还要求 unverified = 0 和缺口处置完整，不能只看 declaredAbsent = 0。

3.5.0 的“管理台只能写平台维护证据”边界也需要明确调整：经用户选择目标与确认计划后，管理台作为用户本机配置工具，可以准备该平台环境与配置入口；不具有跨平台业务运行身份。

接入完成必须同时满足：配置回读一致、所需环境及备份证据有效、矩阵有效且 FAIL/NEEDS-INPUT 为 0、conform.floorReached = true、客户端真实工具回环通过、治理及 Git 收口通过。保留 EXPECTED 行的已登记含义，不用缩小能力并集来刷绿。

核心轮估算约 24 小时工程工作；软件下载、系统安装、重启等待另计。P6 交付通用接线和一个真实客户端的零 AI 回环，不承诺未经验证的六客户端全部适配成功。P1 清单发现需要额外厂商扩展时，逐客户端另立 2–3 小时 P 块并定稿后执行，不能在本轮顺手扩范围或以“通用 MCP 可连”代替客户端验证。

首个真实平台应选择已安装且具有可回读客户端入口的一家，由 P1 的实探决定；没有真实客户端的 dsh 不能作为“全部成功”的验收样例。它可用于缺口修复/等待状态测试，安装并适配真实客户端后再通过同一向导正式认证。
