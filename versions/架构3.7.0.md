## 0. 本代解决什么

3.6.0（2026-10-01，管理台自动接入）之后，运行代继续演进到 `wf-runner 0.13.1` / 管理台 `0.8.14` / 七平台，但治理文本停留在 0.4.x 口径，形成 **SSoT 分裂**；同时门禁、重铺、备份恢复仍靠人工。3.7.0 不新增能力面，只做三件事：**收编增量、机制化防复发、把两个子项目拉回同源**。

## 1. 架构边界（不变项）

- **BP-1~BP-7 上位**：三仓骨架不可变、平台对等、验收最小量、跨平台续跑等价、分步实施与完成判定、入库先行、不可入库件隔离与备份。
- **三共享仓**：`tool`（工作流）+ `agent`（专家）+ `software`（软件配方），同构形态为 `current.json` 指针 / 语义化 `versions/` / 逐版本 `SHA256SUMS` / 依赖锁钉版 / 一句话切默认；已发布版本只读。
- **一级目录（15 个）**：`codex` `dsh` `workbuddy` `zcode` `doubao` `qoder` `qoder-cn` `tool` `agent` `software` `inbox` `versions` `.zcode` `docs-site` `architecture-manager`。本代**不新增、不改名、不迁移**任何一级目录。
- **7 个运行平台**相互隔离；平台私有产物只写本平台 `runtime/`；被声明为项目状态的内容经带 sha256 的 `handoff-bundle/v1` 交接，任何平台不得直读别平台 `runtime/`。BP-4 已撤销跨平台并行仲裁，代价明写。
- **档位口径**对全部工作流统一：未写 = 草稿、过图 = 非严格 QA、交稿 = 全阶段 + 冻结；数模不再有专属链路。

## 4. 双平面：治理架构 + 软件产品

**治理架构平面**：BP 上位 → 三仓同构 → 7 平台隔离 → `wf-runner` 引擎与契约 → `versions/` 治理文本与证据台账。能力并集由共享侧从三仓 registry 集中算一次，对所有平台逐字相同；接入完成判据 = `0 declaredAbsent`；结论不互抄。

**软件产品平面**：`architecture-manager` 是 12 域 + 3 入口（`main.mjs` / `cli.mjs` / `preload.cjs`）的 Electron/React 产品；单条 `conform` 门禁（lint → preload → runtime-drift → governance-drift → tests）；`docs-site` 是白名单源文同步 + C1…C11 独立门禁的静态站；发布为「私有治理仓唯一维护源 + 公开仓白名单导出 + 双包 SHA256SUMS」双仓模型，`versions/anchor.json` 是机器可读选版锚。

**两套门禁独立**：管理台 `architecture-manager-conform/v1` 的 digest 与文档站 `sourceLockDigest` / `generatedDigest` 不是一回事，收口报告分别给值；任一套红都不算完成。
