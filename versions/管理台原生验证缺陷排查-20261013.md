> 排查对象：architecture-manager 对 workbuddy 平台的「客户端验证入口」（`probeNativeClientWithAi`，channel `onboarding:native-ai-probe`）。
> 方法：A/B 实测（同 argv 同配置，仅环境变量不同）+ 全链路代码走查（manager → job_controller → native_workbuddy.py → 厂商 CLI → MCP service → 模型）+ 厂商 bundle 协议层取证 + 台账比对。

## 2. 根因链详述（D-146）

**链条**：agent/宿主进程树 → `probeNativeClientWithAi` env 构造 → job_controller → native_workbuddy.py → 厂商 CLI serve bootstrap → EndpointProviderImpl → CliExecutor。

1. `native-ai-probe.mjs:57` 构造 CLI 环境：`const env={...process.env, ELECTRON_RUN_AS_NODE:'1', ...}`——**原样继承宿主全部环境变量**，未剥离任何注入项。
2. 本机 agent 会话跑在 WorkBuddy 桌面应用进程树内，被注入 57 个变量，其中 `SERVER__PORT=16279`、`SERVER__HOST=127.0.0.1`、`CODEBUDDY_SERVICE_PROXY_URL=http://127.0.0.1:16279/...`（应用给子进程用的 service-proxy 端口，由其 prewarm 池进程 `codebuddy --prewarm` 持有，netstat 实测 LISTEN）。
3. 厂商 CLI serve bootstrap（`codebuddy-headless.js`）：`listen(parseInt(process.env.SERVER__PORT||"")||DEFAULT_SERVER_OPTIONS.port, SERVER__HOST||"127.0.0.1")`，默认端口 3000。继承 16279 → **EADDRINUSE**（CLI 日志 `unhandledRejection listen EADDRINUSE 127.0.0.1:16279`）。
4. `EndpointProviderImpl.get()` 返回的 promise 只由 `setServer(server)` 在 server 绑定后 resolve；绑定失败无人 reject、无人兜底 → **永久 pending**。
5. `CliExecutor.execute()` 首行 `await endpointProvider.get()` 无超时 → 日志停在 `[Startup] CliExecutor: waiting for endpoint...` → stream-json 模式永不启动 → initialize 控制请求永不应答 → `native_workbuddy.py` 60s 超时 → 掩码报 `NATIVE_CLIENT_CONNECTION_FAILED`（真实异常被 `str(exc).startswith('NATIVE_')` 过滤器吞掉）。

**A/B 实证**（同 argv、同 `.mcp.json`、同账号，唯一变量是环境）：

| | 未剥变量 | 剥掉 `CODEBUDDY_*`/`SERVER__*`/`CLAUDE_*`/`WB_*` |
|---|---|---|
| CLI 到达 initialize 应答 | 65s+ 无任何响应 | **7s** |
| endpoint | 永悬（`waiting for endpoint...` 后静默） | `endpoint ready: http://127.0.0.1:61911`（160ms） |
| `[InitializeHandler]` | 无 | 有，`models count=20 currentModelId=fast-model` |
| MCP service | 卡 `connecting` | `instantiateServer stdio` + 直驱握手 0.8s 正常 |

**同类潜在面**：`applyNativeClient`（`native-client.mjs:62`）注册路径同样 `...process.env` 带 `CODEBUDDY_CONFIG_DIR=<隔离 home>`——因 `mcp add-json` 不需要本地 server 暂未触发，属同族潜在缺陷，建议同批修。

**修复方向**（§6 P1）：探针/launcher 构造子进程 env 时剥离 `/^(CODEBUDDY_|SERVER__|CLAUDE_|WB_)/`，或显式分配空闲端口写入 `SERVER__PORT`（注意 `SERVER__PORT=0` 无效——`parseInt("0")` 为 falsy 会落回默认 3000；正确做法是 manager 侧先占端口 0 取空闲端口号再显式写入）。

## 3. 其余缺陷详述

### D-147 AI 探针绑定校验弱于直连探针
- `native-ai-probe.mjs:41` 只校验 `sha256File(profile.configPath)===record.nativeConfigSha256`（`.mcp.json` 配置哈希）。
- 直连探针 `native-client.mjs:126` 校验 `json(profile)!==json(record.profile)`——**全量 profile**，含 `bodySha256`/`cliSha256`/`executableSha256`。
- 实证：WorkBuddy.exe 自 10-08 注册后已被应用自动更新（记录 `55d08c35…` → 实测 `fd43162e…`；app 5.7.7 / CLI 2.156.0），`native-client.json` 里 `profile.bodySha256` 已过期，AI 探针仍放行运行。
- 影响：AI proof 可能绑在与直连探针承认的不同的厂商字节上；两条路径判据不一致。
- 修复方向：AI 探针补全量 profile 比对（与直连探针同源），本体变更时明确拒绝并提示重新注册。

### D-148 单发单校、无模型钉扎、无重试
- argv 无 `--model`，模型走账号 "auto" 路由 → 本次落到 hy4-preview；initialize 响应列 20 个模型（fast/balanced/deep/hy4-preview/hy3/step-5-preview/…）。
- 实证（ai-7ddc3fe4 trace）：思维链明写 "So I should issue function call"，输出却把 `{"challenge":"…","platformId":"workbuddy"}` 当 **文本**吐出，零 tool_use → `validateNativeAiEvents` 抛 `NATIVE_AI_TOOL_TRACE_REQUIRED`。工具在列表第一位、MCP `connected`、schema 简单——纯模型输出格式失败。
- 已排除的环境杠杆：实测 `CODEBUDDY_CURRENT_MODEL_ID=step-5-preview` **不能**改变 CLI 的 `currentModelId`（仍 `auto`）；`--setting-sources ''` 已禁 settings。钉模型只能改 argv。
- 修复方向（两选一或组合）：① launcher 内**同进程有界重试**（新鲜 challenge，免二次登录，共享代码零平台常量，符合 BP-2）；② 平台侧配置支持模型覆盖（写平台自己的 bridge 配置，不写共享代码常量）。注意 `--max-turns 1` 与重试的相互作用需实测。

### D-149 时限失配与误报
- `native_workbuddy.py:40` initialize 时限 60s。实测 CLI 在活配置目录下启动到 initialize 应答 7s（剥变量后），但插件/市场阶段在桌面应用并发下有 36s 的实测记录（marketplace journal 恢复争用）——60s 余量薄。
- CLI 自身 auth 超时 60s（attempt 1 日志：auth 请求 12:06:22.500 → `Cancelled control request: auth` 12:07:22.500），而 launcher auth 窗口 240s——launcher 在等一个 CLI 早已弃掉的请求。
- 超时异常被 `native_workbuddy.py:122` 的 `startswith('NATIVE_')` 过滤器掩码成 `NATIVE_CLIENT_CONNECTION_FAILED`，boot/auth/model 三类超时不可区分。
- 修复方向：分类超时分别报错；initialize 时限上调或改心跳；auth 窗口与 CLI 实际超时对齐。

### D-150 共享认证库并发Mutation + key 可用性竞争
- 实证一（ai-ebac86b8）：启动时 `hasAccessToken=true`，但刷新会话被 `Discard refresh: session changed before persistence`（共享认证库在 CLI 读取后被改写）→ 模型 API 拒 `Authentication required`。
- 实证二（ai-851e0964）：`Discard login: a newer auth operation won`——连开多个 CLI 实例各自发起 auth 操作互相踩。
- 实证三：`AtRestEncryption adapter=credential-fields` 在 read 时 `missing-key`、同会话 write 时 `recovered`——key 可用性存在时序竞争。
- 实证四：浏览器登录成功（ai-7ddc3fe4）后盘上无新增 token 文件（12:14–12:17 窗口仅 audit-log/plugin-status 噪声）——token 不跨进程持久化，每次 attempt 必须真人重登。
- 影响：验证必须人肉在场；快速重试自干扰；登录成果不可复用。
- 修复方向：attempt 串行化 + 间隔退避；明确文档化「每次 attempt 需一次新鲜浏览器登录」；评估「登录与验证同进程单流」方案（登录成功后不退出、直接发验证 prompt）。

### D-151 `.called` 标记按 config 级作用（修复轮执行期新登记，**未修**）
- `mcp_service.py` 对 `architecture_verify` 的双闸：进程内 `probe_called`（单进程内一次）+ 磁盘标记 `Path(sys.argv[3] + '.called').open('x')`。`sys.argv[3]` 是 **config 路径**（`workbuddy-config.json`），标记文件名**不含 challenge**。
- 后果：跨 attempt（新进程、新 challenge）后 `probe_called` 重置但 marker 仍在 → `FileExistsError` → 后续任何 attempt 的验证调用失败。史上无成功验证故尚未触发；**首次成功验证后才显现**，届时需手工删 `bridge/workbuddy-config.json.called` 才能继续。
- 处置：按 BP-5「执行期新发现的非阻断缺陷只登记」，本轮只登记不修；修法（标记按 challenge 作用或 manager 侧清理）须保持「一次授权读取」语义不被放宽，另立 P 表。

## 4. 与 D-123 / D-127 的关系

- D-123（open，「注册成功后无模型直接调用接口仍未验证」）与 D-127（open，「内置工具仍被列出且认证成功不代表工具通道已认证」）是本案的**现象面**，自 10-09 挂起；10-07 修复记录 P6 已记「浏览器登录成功仍未取得有效工具回执」。
- 今日推进：登录链路实测可通（ai-7ddc3fe4 全程 `native_auth_ready` → 模型轮 → MCP connected），把「未验证」从「登录都过不去」收窄到「模型工具调用格式不稳 + 认证库并发干扰」两个可定位点。
- 两条**保持 open**（验证仍未通过）；其 evidence 已追加今日读数与溯源路径。
