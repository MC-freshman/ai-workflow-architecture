## 一、一句结论

**这不是"某处配错了"，而是同一个版本事实被登记在四个地方、由两套互不相通的规则各自校验，且没有任何"以谁为准"的权威。**

`dsh` 自己那一套是**唯一自洽**的：`wf-runner 0.12.2` 的 manifest 声明还要 `repo-lint 0.6.5`（`tool/wf-runner/versions/0.12.2/manifest.json` 的 `dependencies.workflows['repo-lint']`），dsh 的 `scannerRelease` 与 `bridge.json` 默认都是 `0.6.5`。冲突来自**判据工具**：矩阵按共享 `current`（`0.6.3`）显式传版，而平台默认（`0.6.5`）根本没被征询。

**"做版本兼容"这条路在当前架构里不可行**（理由见第五节，硬证据：引擎全文无任何范围/兼容声明，`resolution.py:180` 是逐字相等比较）。**真正的解是两件**：① 把"判据选格"与"平台声明"对齐（管理台侧一处小改，实测可解，见第六节路 B）；② 把"版本对齐"做成管理台里的一等事务操作，并补上现在完全缺失的一致性检查（第六节路 C/D）。

### 2.3 结构缺陷：runner 的声明是冻结的，平台钉版是移动的

上表最后一列暴露的规律：**runner manifest 里 `dependencies.workflows['repo-lint']` 是发版时冻结的文本，而平台的 `scannerRelease` 是会随采纳波移动的路径指针。** 两者没有任何机制保持同步：

| runner pin | 它声明要的 repo-lint | 现实里的平台钉版 | 结果 |
|---|---|---|---|
| 0.12.0（codex/zcode/qoder） | 0.5.1 | 0.6.3 | 声明落后 3 代 |
| 0.10.1（workbuddy） | 0.5.1 | 0.5.2 | 声明落后 1 代 |
| 0.10.0（doubao） | 0.5.1 | 0.5.1 | 恰好相等 |
| 0.12.2（dsh） | 0.6.5 | 0.6.5 | 恰好相等 |

而管理台的**唯一**预检恰好拿这条做硬门（`onboarding-config.mjs:82-83`：runner manifest 声明的 repo-lint ≠ 本次选的 scanner ⇒ `VERSION_PAIR_MISMATCH`）。**注意引擎自己从不检查这条**：`resolution.py:157-161` 对 runner 只跑 `integrity()`（核 SHA256SUMS），`resolution.py:169/174/195-199` 在构造 `workflow:repo-lint` 行时直接用平台的 `scannerRelease` **覆盖**闭包里的同名条目 —— 所以"runner 自述"在运行时既不是约束也不入锁，它**只活在管理台的接入闸门里**。

⇒ **后果：六个平台里有四个只要重跑一次完整接入，就会被管理台自己的预检拦下**（dsh 与 doubao 因两端恰好相等而通过）；而能满足这条硬门的组合只有三种 —— 要么把检查器退回各自 runner 声明的 `0.5.1`（比共享指针还落后两代）、要么**为每个平台发一个恰好声明该平台钉版的 runner 新版本**（版本号与平台钉版强耦合）、要么改这条闸门的语义（路 B 第 3 条）。前两种都不可接受。

**这就是"同批对齐"守不住的真正机理**：不是有人忘了同批，而是**这条不变量的两端根本不在同一个变更里** —— 一端随 runner 发版冻结，另一端随平台采纳移动，而校验器却在每次接入时要求它们逐字相等。历史上每一次"分开动"因此都变成一次 fail-closed 的真实阻断（已有 12 次记录，见 §2.5）。dsh 之所以自洽，是因为它挑的 `0.12.2 + 0.6.5` 恰好是已封存的推荐配对（`架构管理台统一实施P7记录-20261003.md:5`），两端碰巧撞上。

## 三、失败机理：三个环节缺一不可

### 环节 1｜同一个事实，四处副本

| 副本 | 位置 | 谁读它 |
|---|---|---|
| ① 共享 `current.json` | `tool/<id>/current.json` | 矩阵选格、`readOnboardingConfig` 的默认值 |
| ② 平台默认 | `<platform>/bridge.json` → `defaults.workflowVersions['repo-lint']` | 引擎 `resolution.py:39-44`（平台作用域覆盖） |
| ③ 平台钉版 | `<platform>/bridge/<id>-config.json` → `scannerRelease`（**绝对路径**） | 引擎 `resolution.py:163-189`、conform、矩阵 |
| ④ 引擎 manifest 声明 | `tool/wf-runner/versions/<v>/manifest.json` → `dependencies.workflows['repo-lint']` | 管理台 `onboarding-config.mjs:82-83`（`VERSION_PAIR_MISMATCH`） |

### 环节 2｜两套校验，各管一段，互不相通

- **引擎（运行时）**：只有当"被选中的目标恰好是 `workflow:repo-lint`"时，才把选中版本与 ③ 比对，不等即 `VERSION_CONFLICT`（`tool/wf-runner/versions/0.12.2/resolution.py:180-189`，清单 §8.17 D-52 记过同一机制）。
- **管理台（接入时）**：只校验 ④ vs ③（`architecture-manager/src/onboarding-config.mjs:82-83`）。

⇒ ①与②、①与③、②与③**三对关系完全没有校验器**。

### 环节 3｜判据选格不看平台声明（本次失败的直接原因）

矩阵的取版顺序是"显式 `--targets` 覆盖 → 否则读共享 `current`"：

- `tool/architecture-ops/versions/1.5.2/architecture_ops/invocation_matrix.py:545`：`version = current.json.version`
- 同文件 `:586`：`"target": {"mode": kind, "id": ident, "version": str(version)}` ← **显式带版**
- 而引擎的优先级是"显式版本第一，平台默认第二"（`resolution.py:37-47`）⇒ 平台默认被静默跳过。

管理台的认证链路**没有传** `--targets`：`architecture-manager/src/platform-check.mjs:152` 只拼 `--config/--out/--runs-root`（`:156/:158/:159` 追加 progress / exceptions / `--only`）。全仓唯一传 `--targets` 的是单格冒烟 `src/domains/intake/smoke.mjs:25`。

### 为什么"同批对齐"守不住

接入流程**本来**是自动对齐的：`onboarding-config.mjs:114` 就用 `scanner.version` 去写 `bridge.json` 的默认值。问题在于这套对齐**只在接入那一刻发生一次**，之后：

- 判据格按共享 `current` 生成，不随平台声明变化；
- 管理台**没有**任何"只抬平台钉版"或"批量抬版本"的操作（`app/operations.json:546-581` 的 planKinds 全表无 align/upgrade/adopt 类 kind；平台钉版的唯一写入者仍是整条接入流水线 `onboarding-config.mjs:85,91,116`）；
- **完全没有**"平台钉版 vs 共享 current"的一致性检查（全仓无比较代码；`platform-check.mjs:48` 只验路径存在）。

⇒ 结论：**这是一个缺校验、缺权威、缺工具的结构性缺口，不是操作失误。** D-31 早已登记过同一件事："共享侧没有带 checkpoint 翻 `current.json` 的工具 ⇒ 采纳波仍靠各平台手工配对，与 D-52 同族"（`versions/架构3.1.0-更新方案-20260920.md:220`）。

## 五、为什么"兼容版本"这条路不可行（必须明写）

1. **引擎没有兼容概念**：`wf-runner 0.12.2` 全文检索 `compatib|Specifier|>=|Version(` 无任何版本范围判定；`resolution.py:48-50` 只做"精确语义版本"合法性检查，`:180` 是逐字相等比较。声明"两版兼容"没有承载字段。
2. **版本号在这里是内容哈希的替身**：`resolution.py:156,174,179` 把 `manifest.json` 与 `SHA256SUMS` 的 sha256 写进 run-lock。让"两个不同版本都算合格检查器"，等于让两套不同字节都对同一把锁自称权威 —— 与"跑完可回读、可复算"的红线直接冲突。
3. **"全局共享"与"平台独立钉版"是原则级冲突**：共享 `current` 是一个全局默认，平台配置是独立钉版（BP-2 要求结论不互抄、各自自证）。所以版本必然分叉；**能做的不是消除分叉，而是给分叉定规矩**：哪些必须逐字相等（`scannerRelease` ↔ 平台默认 ↔ runner 声明），哪些允许不同（相对共享 `current`）。

⇒ 由此得出一条判据，本方案的其余部分都从它派生：

> **判据必须尊重平台声明，但必须让"落后"可见。**

## 六、候选解（A/B/C/D/E，含代价与风险）

### 路 A｜撤销 dsh 的本地统一回 0.6.3
- 动作：`dsh/bridge/runner-config.json` 的 `scannerRelease` 与 `dsh/bridge.json` 默认都改 `0.6.3`。
- 代价/风险：**撞管理台预检** —— `wf-runner 0.12.2` 的 manifest 声明要 `0.6.5`，`onboarding-config.mjs:82-83` 会报 `VERSION_PAIR_MISMATCH`。等于要退回 `wf-runner ≤ 0.12.0`（与 codex 同代），并把 dsh 的判据 pin 一起退。
- 结论：**不推荐**。它让唯一自洽的平台去迁就一个自身不自洽的共享指针栈。

### 路 B｜判据按平台声明选格 + 重新裁定"声明"的语义（推荐作为根治点）
- 动作（四处，均属管理台/工具面，不动共享字节、不动他平台配置）：
  1. `invocation_matrix.py`：选定行的版本改为"显式 `--targets` 覆盖 → **平台 `bridge.json` 默认** → 共享 `current`"三级，与引擎 `resolution.py:37-47` 的优先级逐字同构；行内增记 `resolvedFrom`（消除"默认来自哪一层"的歧义）。
  2. `platform-check.mjs:152` 起的 `matrixArgs`：当平台对该资源声明了默认版本时，传 `--targets kind:id@<平台版本>`。
  3. **重新裁定 `onboarding-config.mjs:82-83` 的预检语义**（关键，否则四个平台仍被拦）：runner manifest 的 `dependencies.workflows['repo-lint']` 是**发版时该引擎所测的配对代**，不是"运行时必须逐字相等的硬约束"（引擎自己在运行时不执行这条；只有"被选中目标恰为 `workflow:repo-lint`"时才比对 `scannerRelease`）。因此该值应当降级为**记录与建议**：接入时以它作为默认推荐值，不一致时给出**具名警告**（写进接入记录与治理登记），但**不阻断**；真要阻断，只能按"平台钉版不得早于 runner 声明"这类可判定的关系来判，而不是逐字相等。
  4. 判据版本自证：`--print-digest` 已存在，平台在 `invocationMatrixRelease` 里钉判据代（dsh 已钉 1.5.2）—— 保持。
- 代价：改判据工具 + 管理台一处预检 + 测试 + 出包（管理台 0.5.3 / architecture-ops 新版本件），再用新包跑一次续跑。
- 风险与缓解：**风险**＝预检放宽后，"平台钉版与其 runner 声明不一致"这种真问题可能被无声放过。**缓解**＝不一致必须落进认证报告与登记（具名 + 代数差），并交给路 C 的检查项常驻显示；"放宽"的是阻断，不是可见性。
- 实测支持：§2.4 的 A/C 分支证明按平台声明选格必然通过。

### 路 C｜管理台新增"版本对齐"一等操作（用户要的"一键更新"）
- 现状：**不存在**。已有的是单资源逐个切指针（`plans.mjs:53-67`、`transactions.mjs:200-240`），平台钉版没有独立写入操作。
- 目标形状（复用现成事务内核即可，不需要新机制）：
  - **检查**：plan kind `version-alignment-report`，逐平台算并列出 ①共享 current ②平台默认 ③`scannerRelease` ④runner manifest 声明 四个读数，标出"必须逐字相等"的三项是否一致、以及相对共享指针是"最新 / 落后 N 代 / 领先"。
  - **修复**：plan kind `align-platform-generation`，在**一个事务**里写 `bridge.json` 默认 + `<id>-config.json` 的 `runner/contracts/scannerRelease/invocationMatrixRelease`，写完按 `onboarding-config.mjs:82-83` 的同一条规则回读复验（`kernel.mjs:56-59` 的 plan schema / 二次确认 / checkpoint / `atomicWrite` / 逆序回滚全部沿用）。
  - **推荐而非盲拼**：0.5.0 手册与 P7 记录已经确立了"按冻结 manifest + 依赖配对算推荐组合，不取三个最新字符串"的原则（`versions/架构管理台0.5.0使用手册-20261004.md:91`、`架构管理台矩阵增量认证与提速方案P表-20261003.md:42`）。对齐操作应当是这一原则的**执行器**。
- 代价：一处新 plan kind + 面板 + 测试；不需要新事务机制。不改运行语义，**不改变任何平台能力**（BP-2/BP-3 的"结论不互抄"不受影响，各平台仍各自出证）。

### 路 D｜共享指针的代际成套（治"新平台默认路径坏了"）
- 现状：`wf-runner 0.12.0` 要 `repo-lint 0.5.1`，指针却是 `0.6.3`；`0.12.2 + 0.6.5` 是已封存的推荐配对（`versions/架构管理台统一实施P7记录-20261003.md:5`）但从未切共享默认。
- 两条子路：
  - **D1（抬针）**：把 `tool/repo-lint/current.json` 抬到 `0.6.5`（可选同时抬 `wf-runner` 到 `0.12.2`）。效果：共享栈自洽、新平台默认路径可用。代价：**属采纳波** —— 各平台下次按共享值选格时需各自自证（BP-2），且需共享仓写入授权与推送通道。
  - **D2（补判据）**：把"共享指针栈必须自洽（runner 的声明 == repo-lint 指针）"写成 `repo-lint` 的一条常开检查或管理台的一致性检查项，使不自洽**当场可见**，而不是等下一个人来接。
- 建议：**D2 先做（成本低、纯增量），D1 作为单独授权的采纳波**。

### 路 E｜判据自身的三处版本声明必须自洽（本次才看见的一类）

上面 A–D 治的是"跨位置"的失配；还有一类是"**同一个释放件内部**"的失配，已复发三次（D-95 `repo-lint 0.5.2` → 本次 `repo-lint 0.6.4` → 本次 `runtime-contracts 1.5.1/SOURCE.json`）。它的代价与跨位置失配一样大：一个自述错版的释放件会被严格身份检查整件拒用（U-01 就是这么阻断 P7 的）。

- 动作：把"`manifest.version` == 目录名 == `workflow.yaml` 自述版 == `SOURCE.json.version`"做成发布前/常开的一条机器检查（`repo-lint` 现有 R2 只查 manifest 与目录，未覆盖 workflow.yaml 自述与 SOURCE）。
- 代价：极小（判据里加一条逐字比较），收益是永久消灭这一族。
- 注意：**已发布字节不可改**（红线 1），检查只对今后发版有效，盘上两条按"只登记"处理。

### 明确不做
- 不给引擎加"版本兼容/范围声明"（第五节三条理由）。
- 不做自动跨平台抬针（违反 BP-2 各自自证；且 D-52 已裁定：翻共享 `current` 会改变他平台可调用面，本平台不得代其验证或申报）。

## 八、本方案不解决的部分（诚实边界）

## 十、本轮补测：版本面的真实规模与三条新发现（2026-10-06 20:0x）

### 10.1 版本面到底有多大（实读，2026-10-06 20:05）

| 面 | 规模 | 谁发布 | 谁钉版 | 现有机械校验 |
|---|---|---|---|---|
| 共享 `current.json` 指针 | tool **1 853** 份 / agent 15 份 / software 8 份 | 各仓发布动作 | 平台 `bridge.json` 默认、矩阵选格 | 矩阵按指针取版；**指针相对"最新已发布"是否落后无任何检查** |
| `versions/` 释放目录 | tool **1 936** / agent 30 / software 25 | 同上 | run-lock 逐行钉死 | 引擎严格闭包 + 双哈希（**有机制、很少失配**） |
| agent `tool-lock.json` | **30** 份 | 专家作者 | 专家自身 | 引擎按锁解析（有机制） |
| 平台 run-lock | **225** 份（六平台合计），内含 skill 资源行 **860** 条 | 每次 run | 引擎 | 续跑逐资源哈希复验（有机制） |
| 已发布 manifest 的跨资源依赖 | ≈ **244** 条 | 各资源作者 | 引用方 manifest | 引擎严格闭包按选中代解析（有机制） |
| **平台工具链四键** | 六平台 × ≤4 键 | 用户/管理台 | 平台 config + bridge 默认 | **只在接入那一刻查一次，运行时不查** |

**这张表解释了"为什么到处都撞版本问题"的观感与实际**：技能池/专家池的"作者→钉版"失配有机制兜着、且被严格闭包挡住（失配即拒，很少静默）；**真正没有守卫的只有"平台工具链四键"这一小块** —— 而它恰好在每次接入、每次矩阵里被反复踩。

⇒ 结论（也是给 P2/P3 的范围约束）：**方案必须停在工具链 + 判据 + 共享五个治理指针这个范围内**，不得扩成"全仓 1 853 个指针的核对"，那既违 BP-3，也解决不了本案。

### 10.2 新发现一：管理台的版本下拉是平铺的，没有配对提示

`renderer/panels/onboard.jsx:82` 的三个下拉（引擎/契约/检查器）只列"使用共享默认 X"+ 该仓全部可用版本，**不标注哪一套是配对代、也不警告已知不兼容组合**。用户按字面选 `wf-runner 0.12.2 + repo-lint 0.6.3` 这种组合，只会在预览/保存时吃到一条 `VERSION_PAIR_MISMATCH`。

- 现成的正解已经存在一半：同文件 `:81` 的「选择这套提速版本」按钮会写入 `performanceRecommendation` 的**四件成套**值（引擎+检查器+契约+判据）。
- 建议（并入 P2/P3）：下拉里把推荐配对标出来，选中已知不兼容组合时**在预览前**给出具名提示。这不改判据、不改语义，只是把已经算出来的配对结论显示出来。

### 10.3 新发现二：共享指针"全局陈旧"，且没有按资源的采纳状态位

实读：`wf-runner` 指针 0.12.0（已发布 0.12.1/0.12.2）、`repo-lint` 指针 0.6.3（已发布 0.6.4/0.6.5）、`architecture-ops` 指针 1.5.1（已发布 1.5.2）—— **三个指针同时停在"已发布但未采纳"的旧代**，而"发布 ≠ 采纳"这条原则本身是对的（BP-2）。缺的是**采纳状态可见性**：盘上没有"某资源已采纳/未采纳"的状态位，靠人记。

- 建议（并入 P2）：对齐报告除"平台四键 vs 共享"之外，再加一列**"指针 vs 最新已发布"**（对五个治理指针 + software 六件）。这是只读查询，零写入风险，却能一眼看出"哪些代已发布等着被采纳"。
- 注意边界：**报告不得把"落后"判成失败**（落后可能是合法的采纳时差），只做显示与登记。
