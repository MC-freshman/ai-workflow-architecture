# 接入口径裁定（2026-10-28）

本文件记录用户对「接入到什么程度算什么」的口径裁定，以及裁定落到代码后的唯一机器来源。此前 `architectureComplete` 这一个字段名在五处各有各的公式，同一份入驻记录会被引擎给出三种答案（D-167 / D-168 / D-169）；裁定后它们统一到一处。

## 1. 完全接入（用户裁定 2026-10-28）

> **完全接入 = 能够流畅跑通架构管理的所有步骤。**
> 理由：以现在常用的口径为准；早期口径已不再引用，不为旧档回补。

机器来源：**`architecture-manager/src/domains/platforms/adoption-completion.mjs` 的 `readAdoptionCompletion()`**，读 `<platform>/runtime/maintenance/manager-onboarding/automatic.json`（入驻 journal）。判定：

1. `journal.status === 'complete'`（有未解决项或软件未绑定时，apply 只会写 `configured-pending`，因此这一步已经排除跨缺口宣称完成）；
2. **步骤序列 `ONBOARDING_STEP_SEQUENCE` 每一步都在档** —— 缺一步即为未完成；
3. 每一步的状态属于 `{passed, auxiliary}` —— `auxiliary` 不阻断，是 2026-10-13 业主裁定（厂商原生验证只是辅助项，如实记录、不充当完成门槛）；除此以外的任何状态（pending / deferred / failed）都算该步没跑通。

步骤序列（`applyAutomaticOnboarding` 实际走过的 11 步）：

| # | 步骤 key | 含义 |
| --- | --- | --- |
| 1 | `configuration` | 配置与版本 |
| 2 | `backend` | 隔离后端 |
| 3 | `environment` | 运行环境 |
| 4 | `providers` | 平台 provider |
| 5 | `client` | 服务通道验证 |
| 6 | `capabilities` | 能力实测 |
| 7 | `l1-dual-cell` | wf/wfa 真实调用收据（一个 workflow + 一个 agent 真跑 prepare→next→stop） |
| 8 | `native` | 厂商原生三仓验证（默认 auxiliary） |
| 9 | `certification` | 完整认证 |
| 10 | `governance` | 治理登记 |
| 11 | `git` | Git 提交 |

**对旧档的后果（如实，不静默）**：早期 journal 没有 `l1-dual-cell` 这一步，按本裁定**不是完全接入**，其 `pipelineEra` 标为 `pre-criteria`、`missingSteps` 列出缺的步。沿用 2026-10-14 口径：**状态重挣不迁移** —— 旧档不映射为达成，要按当前判据重跑入驻。

## 2. 最小接入（用户 2026-10-28 询问，本轮查明后确立）

> 问：「最小接入」是不是「platform 能够正常通过 wf/wfa 调用 skill」？
> **答：语义上就是；但「最小接入」这个术语此前在代码与文档里都不存在**（全仓检索 0 命中），机器侧只有一个没有名字的等价物。

等价物是 **L1（`l1-dual-cell`）收据**：`selectL1Cells` 从 tool / agent 两个 registry 各取字典序第一个启用且可调用的条目，通过平台 runner 真跑 prepare→next→stop，判定范围 `scope:'invocation'`。它正是 2026-10-13 裁定的产物——**真实工作流调用收据取代够不到的厂商原生读回执，成为「连得上」的判据**。

因此本轮确立命名：

- **最小接入（L1）** = platform 能正常通过 wf/wfa 调用 skill；机器来源 = journal 中 `l1-dual-cell` 步为 `passed`（`readOnboardingThreeLayer().l1.status === 'achieved'`）。
- 与「调用面覆盖」区分：`platform-check.mjs:247` 的 `invocationCoverageComplete` 是 scope='invocation' 的整体覆盖读数，比 L1 宽，不是最小接入。
- 与「完全接入」区分：最小接入只回答「跑得通调用」；完全接入要求 11 步全跑通。

## 4. 关闭的缺陷

D-167、D-168、D-169 三条同源（同一字段五套公式），随本裁定与统一实现一并关闭。回归用例见 `architecture-manager/test/adoption-completion.test.mjs`（7 例）与 `test/onboarding-chain.test.mjs` 的「两个机器来源给一个答案」用例。

**受本裁定影响的既有 fixture**：`test/three-layer.test.mjs` 原来的「complete journal」只写 3 步（configuration / l1-dual-cell / certification），按新裁定它不是完全接入，L3 因此落到 `stale-era`。该 fixture 已补全为 11 步序列；同类的 `test/onboarding-full-adoption.test.mjs`、`test/onboarding-native-auxiliary.test.mjs` 的 journal helper 也一并按序列造数。改任何一处判定后**必须重跑全量**，不能再只复跑「相关文件」。
