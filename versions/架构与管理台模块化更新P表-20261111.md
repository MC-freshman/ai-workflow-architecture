## 1. 项目概况

### 1.1 目标与定位

`E:\ai` 是一套**本地多客户端 AI agentic workflow 治理架构**：把「工作流 / 专家 / 软件配方」沉淀为可冻结、可哈希回读、可跨客户端共享的版本化资源，让 7 个 AI 客户端（codex / dsh / workbuddy / zcode / doubao / qoder / qoder-cn）在同一套规则下钉版运行、等价续跑，并用一个本地桌面管理台把盘点、接入、发布、备份、Git 收口变成「先出可核对计划、再执行获准更新」的受控流程。

### 1.2 现有架构（治理平面）

- **三共享仓（BP-1 骨架不可变）**：`tool`（工作流）+ `agent`（专家）+ `software`（软件配方，只存文本不存本体）。同构形态：`current.json` 指针 / 语义化 `versions/` / 逐版本 `SHA256SUMS` / 依赖锁钉版 / 一句话切默认；已发布版本只读。
- **现行运行代**：`wf-runner 0.13.1` / `runtime-contracts 1.6.0` / `repo-lint 0.7.0` / `architecture-ops 1.5.2` / `platform-conformance 1.6.3`（`versions/anchor.json` 机器锚）。
- **引擎能力**：四种阶段动作（prompt / script / software-call / process gate），`run-lock.json` 钉版、事件流、幂等与崩溃拒绝（`REVISION_CONFLICT`）、`handoff-bundle/v1` 跨平台续跑交接、三档 rigor（草稿/过图/交稿）。
- **平台隔离（BP-4）**：私有产物只写本平台 `runtime/`；项目状态经带 sha256 交接载体读回；跨平台并行仲裁已撤销（代价明写：同项目双客户端同时开会互相覆盖）。
- **治理文本**：`versions/` 基线序列（现行 `架构3.7.0.md`）+ 缺陷状态簿（172 条：closed 147 / ruled 13 / absorbed 3 / open 8 / unverified-registration 1）+ 平台接入清单。
- **软件面新形态（2026-11-07/08 已落地）**：`software/architecture-manager-mcp@3.0.0`（21 工具，自动白名单覆盖管理台 363 个真实函数：只读 290 / 写 60 / 红线 13）与 `ai-novel-platform-mcp@3.1.0`；通用确认写 `*_apply`（一次性 planId/confirmToken、删除需 ack）。

### 1.3 管理平台能力（产品平面，architecture-manager 0.9.0）

- **形态**：Electron 44 + React 19 + Vite 8 桌面应用，Node ≥24；12 域 + 3 入口（`main.mjs` / `cli.mjs` / `preload.cjs`）；安装包自带三仓 seed（空工作区自动铺放、逐文件 SHA-256 校验）。

- **IPC 面**：`app/operations.json` 声明 116 通道（query 42 / plan 44 / execute 21 / ui 7 / verify 2），读写按 phase 分离；preload 由脚本生成；`register-operations.mjs` 手写通道字面量，由 `module-boundaries.test.mjs` 5 组断言钉住三方一致。
- **业务能力**：11 步入驻流水线（完全接入唯一口径 `readAdoptionCompletion()`）、L1 双格「能用」回执、一键更新所有平台、plan→checkpoint→audit→回读事务、Git 计划与敏感扫描、三仓发布、软件接入/健康/恢复、缺陷簿与审计完整性核对、run 台账只读盘点。

- **MCP 入口**：管理台能力经共享配方 `architecture-manager-mcp` 暴露给 AI 客户端（GUI + CLI + MCP 三入口）；注入层绑定源码函数签名，**升级后须人工重跑探针**（维护期项）。

### 1.4 使用场景

1. **新工作区接入**：安装 EXE → 指向空根目录 → seed 铺放 → 平台接线 → L1 双格 → 厂商客户端加载入口技能。
2. **日常治理**：一键更新所有平台、三仓资源发布/选版、软件本体接入与配方冻结、备份恢复演练、Git 收口推送。
3. **AI 会话协同**：AI 客户端经 MCP 只读治理现状、按 plan 申请有界写入（确认写），或经 `/wf` `/wfa` 入口技能钉版跑工作流/专家。
4. **审计与排错**：缺陷簿、审计事件完整性核对、run 台账、治理漂移机检、文档站源锁。

## 5. 模块化目标形态（本轮落地部分）

1. **模块清单契约 `ai-manager-module/v1`**（新 schema，ajv 可校验）：每模块声明 `id / kind(domain|panel|view|runtime|gate|entry) / entry / exports / channels / dependsOn / replaceable / replacementContract / healthCheck`。
2. **注册表是派生视图，不是第三声明源**（R1-F2）：`src/app/module-registry.json` 由 `scripts/generate-module-registry.mjs` 从 operations.json + 域导出枚举 + 视图映射**机器生成**，禁手改；新鲜度由 test 段用例钉住（生成结果 == 已提交字节）。避免 D-167/168/169「同一字段多处公式」复发。
3. **拆卸/替换/重组机制**：注册表 `enabled` 开关 + `replacement` 指向（默认 null=原实现）；面板按视图懒加载，拆卸后显示统一空态「模块已拆卸」；替换实现必须通过**契约测试**（同 fixture 输入 → 逐字可比输出一致）才可启用。全部走既有 query/plan 分离，**不新增写通道语义**。
4. **边界**：core/transactions 内核不依赖 Electron、不引用 renderer（既有断言保持）；注册表不得成为绕过 plan→checkpoint→audit 的通道；远程代码一律不加载（CSP 不动）。
