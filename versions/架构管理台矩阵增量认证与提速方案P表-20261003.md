## 2. 管理台怎么改

### 2.1 版本采纳在界面上完成

“完整配置”明确显示“正在使用”“推荐组合”和改变的配置文件。推荐组合依据已冻结 manifest、依赖配对和兼容声明计算，写入预览计划，不依赖把字符串最大的版本当成兼容版本。

目前 0.12.0 / 0.6.3 这组可优先采纳已发布的 0.12.1 / 0.6.4，契约保留原钉版；提交回滚点后，用户确认一次配置计划，再做该平台最小复验。不能只换 EXE 就显示“已提速”。旧 run 必须按原锁继续或停止。

WorkBuddy、Doubao 是更早的组合，需要单列兼容迁移预览，不能把它们算成同代补丁。其迁移和独立认证按各自配置执行，不继承 Codex 的通过读数。

新平台配置默认推荐通过配对检查的性能版本；已有平台保留当前值并明确提示未采纳。共享 current 的切换不是本轮默认动作。

### 2.2 所有入口使用同一个范围判定器

主按钮改为“检查接入”，点击前说明“本次实测多少格、沿用多少格、为什么”。平台面板、自动接入、继续检查和失败重试调用同一判定器。

| 情形 | 实际动作 |
|---|---|
| 首次平台接入，或引擎/契约明确的大版本升级 | 本平台完整矩阵一次；能力地板和客户端回环仍须满足 |
| 已首检，输入及能力均未变 | 校验历史证据来源及内容摘要；做最小入口复验和必要客户端回环，沿用其余行 |
| 一个资源新增、升级或重新启用，复用既有 Profile | 仅该资源和真正受影响的依赖者；不逐平台全矩阵重认证 |
| 某个 provider、解释器、软件登记或 Profile 改变 | 通过依赖关系选受影响格；未知影响保守扩大到相关类别，明确原因 |
| 失败/取消/中断 | 保留已完整成功且输入仍一致的格；只继续失败和未完成格；未收口的 prepared run 先停止 |
| 证据缺失、内容遭改、无法确认来源 | 拒绝沿用对应行；需要重建的范围明确列出，不能显示为通过 |

“强制重跑全部”放到高级诊断，不作为日常接入认证，也不额外建立完成门槛。首次缺失证据时重建覆盖面是必要补证，不能借此让每次修改都重新首检。

关键是**内容摘要和依赖关系**，不是仅看版本号、mtime 或 latest.json：每行记录资源及精确依赖闭包、钉版、相关 config/Profile/provider/environment、验证器与范围规则的摘要，并保存可回读原始报告 sha256。全局 R2 身份规则仍检查，不能因只测一格而放过全局身份漂移。

结果明确分开“本次实测”“沿用历史证据”“失败”“未测试”。合并报告保存旧报告和新报告的来源及摘要；沿用行保留原测试时间。全局 config 的无关文案变化可以重新绑定语义相同配置，真正影响某行的字段必须使该行失效。

### 2.3 减少首次矩阵的进程重复启动

在**新发布的共享 runner/检查器版本**增加明确声明的单格批处理接口：一次 Python 子进程内执行该格的 prepare→next→stop，复用导入模块、已验证的解析缓存及初始化对象。沿用正式 Engine.dispatch 和磁盘状态事务，不复制一套简化判据。

每格独立进程及 run-id；初版继续按格串行，成功工作流/专家的启动次数由每格 3 次降到 1 次。软件格维持其正式网关路径，不混用这个批处理接口。管理台按 manifest 声明选择通道，旧版仍可用原 CLI，并显示兼容模式及其开销。

每一步仍检查应检查的请求、版本锁、状态修订和内容完整性。缓存只缓存可复算的解析结果；不跨请求盲信“文件以前验过”。本轮不加入高并发扫描、常驻后台服务、原生软件会话或业务阶段执行。Windows/WSL 进程生命周期仍由平台自己的 provider/管理台现有 owned-process 管理；取消、超时、关窗都收口，不能留下半个 prepared run。

### 2.4 能看见耗时，能安全继续

进度显示阶段、当前资源、prepare/next/stop、已完成/需实测总数、实耗时、沿用数。报告增加各阶段及初始化耗时，列慢格，方便区分解析、校验、软件连接及系统 I/O。

部分报告逐格原子落盘。取消仍是取消；已有成功行可以作为下一次续检候选，但整个未完成矩阵仍 certifiable=false。恢复前重新核对每格输入摘要和原报告哈希，不能把进度百分比当认证。

本轮顺带处理这些认证入口完成后仍显示忙碌的已登记问题，限于本方案覆盖的任务状态，避免实际结束后还让用户误以为检查未停。

## 3. 有序 P 表

每个 P 预留 2–3 小时墙钟，三个子块均能安全停手；预计工程量 8–12 小时，不是已经实测的工时。进入执行前重新读盘冻结新版本号段及判据。下列目标是拟议验收目标，尚未达成。

| P | 子块与实施方式 | 安全停手产物 | 预定判据 |
|---|---|---|---|
| P1 版本采纳与可比基线 | ① 提交治理/配置回滚点，冻结来源摘要及测试输入；② 用现有配置事务增加推荐组合、保留正在使用及迁移提示；③ 在 Codex 范围采纳既有同代补丁，保存单格阶段计时 | 回滚 commit、配置计划、采纳/未采纳清单、基线报告 | 配对正确、配置可回读；旧锁不静默换代；只做本平台受影响格，其它平台不代出证；无软件安装或共享 current 切换 |
| P2 统一增量认证 | ① 统一所有认证入口并建立每格依赖/输入摘要；② 修正同钉版直接只测 expert-task 的漏选，迁移已有可核实首检证据；③ 做变更范围和失败/中断续检的必要负例 | 候选代码、范围预览、带来源哈希的合并报告 | 未变行不重复认证；资源变更、Profile/provider 变化、文件篡改均不能遗漏；未知 ID/零行不能 PASS；不借他平台 runtime 或结论 |
| P3 单格批处理与耗时显示 | ① 在候选 runner/检查器声明正式接口，每格一次进程走真协议；② 接管理台进度和任务收口，补逐格恢复及完成状态；③ 用同一工作流和有精确依赖的专家比较原 CLI 与候选，验证取消/漂移拒绝 | 冻结前候选、原协议/批处理对比、部分报告、真实取消证据 | 正常行及关键错误分类等价；每成功工作流/专家格 runner 启动 3→1；两代表格各模式 3 次同机串行测量，中位总耗时目标≤原补丁 CLI 的 80%；不能靠省略完整性检查达标 |
| P4 最小验收、双包与入库 | ① 将 P1–P3 必要判据收敛成一条 conform 回读命令；② 发布新冻结目录及管理台双包，实际 EXE 点一次默认增量、取消及续检；③ 更新 README/使用说明，提交两仓、扫描凭据/本体/大文件、正常推送并回读 | 新包、哈希、读回 digest、治理记录及两仓 HEAD | 不新增全矩阵/逐平台重认证；明确本次实测/沿用/未测；新包能用、旧释放版不改；本轮路径 status 空、远端一致、回滚入库早于配置替换 |

阶段验收仅保留能抓本轮真实失败的项：范围遗漏/过度重测、错误沿用证据、协议分类改变、取消残留、版本锁漂移、发布完整性。相关机器判据并入同一条 conform；不得在收口时追加全矩阵。

P3 若未达到预先冻结的性能目标，必须如实记录未达成，不能把启动次数减少当成全部提速完成。不会预先承诺“首次 52 格固定几分钟”；首次总耗时受依赖、provider 和机器 I/O 影响，只能由真机结果说明。
