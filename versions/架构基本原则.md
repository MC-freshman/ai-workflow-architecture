## BP-1　三仓骨架不可变（结构原则）

> 最基本框架：`tool` + `agent` + `software` 共享仓库架构不能变。

**条文**

- **1.1** 三仓的存在、职责边界与同构形态是**不可变项**。任何版本升级、平台接入、外部工具整合，都不得取消、合并、降级其中任何一仓，也不得在平台目录内另建平行的功能面来绕过它。
- **1.2 同构 = 四项对称**，三仓逐一都要满足，`software` 不因"只是配方仓"而豁免：
  ① 目录形态 `<id>/{current.json, versions/<semver>/…}`；
  ② 注册表 + `current` 指针 + 逐版本 `SHA256SUMS` 密封；
  ③ 发布即冻结（新建语义化版本目录 + 翻指针，**永不覆盖已发布目录**）；
  ④ 可被依赖锁精确钉版（专家 `tool-lock` / 工作流 `dependencies`）并可被"一句话切默认"换代。
- **1.3 入仓面只放可冻结、可跨平台共享的文本**：定义、配方、schema、能力快照、selftest、说明书。凭据、本体二进制、运行产物、平台状态一律不入仓。`software/phpStudy_64/` 是**唯一一格已登记存量例外**（用户本人移植、2026-09-18 明示保留）：不得仿照、不得扩大、不得随仓打包分发。
- **1.4 三仓对平台只读**。写入只发生在两个受控动作上——发布新版本目录、切换 `current.json`——且都须用户授权。
- **1.5 新能力品类的归置义务**：任何新品类（外部工具、数据集、模型、素材）必须先判断能否归入三仓之一；不能归入时**先修订本文**再开新仓。禁止用平台本地能力绕过共享层。
- **1.6 环境需求的归属只有三条路**（2026-09-22 用户裁决；取代此前"给某个领域单独钉一套环境"的做法，如数模求解器链）：某个 skill / 工作流 / 场景跑起来需要的解释器、库、外部程序，只能落在以下三处之一，**且必须写明落在哪一处**——
  - **① 装在 agent 里**：作为该专家释放版 `dependencies` / `requiredProfiles` 的一部分声明，随专家钉版；
  - **② 装在 skill 里**：由 skill 声明其环境需求（profile 键或 `dependencies.software` 钉版），**仓内只放声明与配方文本**，真实字节按 1.3 不入仓；
  - **③ 装在所属 platform 里**：由各平台按 recipe / `scriptEnvironmentRungs` 装进自己的 `runtime/`，按 BP-7 隔离与登记，共享件不得出现其绝对路径。
  三者都不构成"为某领域在根级另建一套永久环境"的理由；也不得把 ① ② 的声明写成 ③ 的实测能力（BP-2 的结论不互抄、红线 4）。

**判据**：三仓各自 registry + 指针 + `SHA256SUMS` 齐备可校验；同一平台的 config 内 `toolRoot` / `agentRoot` / `softwareRoot` 三根并存且共用同一套只读绑定；`switch_defaults.py` 对三仓行为一致。

**当前差距（2026-09-22 更正；原为 09-18/09-20 实勘，已被 3.0-A 与三平台采纳超出）**：~~`software/registry.json` 不存在~~ → 已存在（`ai-software-registry/v1`，六行 + 七轴裁定，3.0 S-P2）；~~引擎动作枚举仍封闭为 `["prompt","script"]`~~ → `0.9.0` 起含 `software-call`（`runtime-contracts 1.3.0`）；~~六平台全量 grep `software` 零命中、只绑两根~~ → qoder / codex / workbuddy 三家已声明 software 键并接第三根只读绑定（各自读数见其台账），**zcode / doubao / dsh 仍是"三仓只接两根"**，属 BP-2 的时间差待补，不构成本条骨架缺口。

## BP-2　平台对等与能力地板（能力原则）

> 所有平台接入后均平等，都要能够使用 tool+agent+software 的所有功能。

**条文**

- **2.1 对等项**：所有已完成接入的平台在能力面上地位相等。能力并集由共享侧从 `tool/registry` + `agent/registry` + `software/registry` **集中算出一次**，对所有平台**逐字相同**；不存在任何平台专属的更大功能面。
- **2.2 能力地板**：平台"接入完成"的判据 = 对该并集 **0 个 `declaredAbsent`**（conformance floor）。未达到者处于"接入未完成"状态，列待补台账；**不得**表述为永久分层、主/次平台或"本平台不支持"。
- **2.3 无血统特权**：作者、搭建者、发布者、定稿会话的身份**不产生任何运行时能力**。谁写的、谁发布的、哪个会话定的稿，都不改变该资源在任意平台的可调用性，也不构成任何旁路。
- **2.4 差异只允许来自三处**：① 达标时间差；② 声明式能力面（逐条登记 + 给出补齐路径与成本）；③ 真·物理不可能（须点名 + 说明理由 + 不得由共享代码或文档默认）。**除此以外的任何平台差异都是缺陷**，不是特性。
- **2.5 零硬编码**：共享代码、契约、配方、工作流定义中不得出现平台专有常量、venv 路径、发行版名、release 特例。平台差异只能经声明式接口表达。把某平台的沙箱/授权/路径写进引擎即违反本条。
- **2.6 结论不互抄**：每平台用自己的 config 独立复验。一平台达到的能力不自动让别平台达到，反之亦然；授权类能力（如 D04 只读绑定）逐平台单独取得。
- **2.7 功能不得被开销封顶**：任何为"严谨"而设的固定成本（全量重哈希、全树重扫、满配矩阵）都不得成为功能不可用的原因。功能用不了要按 BP-2 修能力面，**不得靠调低调用档位来"绕开"**——档位只管开销，永远不管能不能用（A/B 两轴正交）。

**判据**：一条 `conform` 命令对每平台输出该并集的覆盖清单（pass / declaredAbsent / 未测），对三仓同口径。

**当前差距**：2.0 四条硬门只有 qoder 与 zcode 各自出证；`dsh` 未接入；qoder 生产 **0.7.7**（2026-09-18 晚）而 codex/zcode/doubao/workbuddy 生产仍 0.6.0——**引擎侧缺陷修在共享仓，但采纳率仍是单机，这扩大而不是缩小对等差距**；doubao/workbuddy 无脚本沙箱；数模求解器链各平台 `declaredAbsent`。3.0 提案 §8.3 原文"高完整度主平台"的平台分层表述**违反 2.2**，已按本文改判（见该节）。

## BP-3　共享优先，验收与接入最小量（成本原则）

> 三仓架构主要是为了实现共享；除必要的时间和 token 消耗，其它验收、接入都要最小量实现。

**条文**

- **3.1 目的条款**：三仓存在的目的是**共享**。除必要的时间与 token 成本外，验收、接入、认证、演练一律取最小量。**"更严谨"本身不构成增加成本的正当理由**——每项开销必须能指明它抓哪一类真实失败。
- **3.2 五条硬约束**：
  ① **风险比例**——验收深度 ∝ 实际改动的爆炸半径，不默认满配；
  ② **增量优先**——用内容哈希定位 delta，未变部分**沿用既有 attestation，不重复认证**；
  ③ **一条命令**——所有机器可判的验收收敛到单个 `conform` 入口，输出一个 pass/fail digest，取代手写多份证据文件；
  ④ **只留能抓真失败的检查**——必留四项：SHA256 完整性、版本入 run-lock、权限/Profile 声明命中、**受影响**矩阵格 FAIL 0；
  ⑤ **重检延到边界**——全矩阵只在**首次平台接入**与**引擎/契约大版本升级**两个时刻跑。
- **3.3 三问闸门**：新增任何验收或接入步骤前必答，三问不过即**不得写入方案**：① 抓的是不是真失败？② 能不能增量？③ 能不能并进同一条 `conform` 命令？
- **3.4 摩擦上限（可验收的量化口径）**：新增/升级一个**复用已声明能力 Profile** 的 tool / agent / software 配方 = 索引追加 + `conform --only <id>` 单格冒烟 ⇒ **零平台改动、零全矩阵、零逐平台重认证**。引入全新能力 = 补 1 条声明 + 单格冒烟。逐字节回滚演练**每引擎大版本一次**（每次发布仍留逐字节备份 + sha256，那是便宜的保险）。
- **3.5 对本原则之后的所有版本同等生效**：包括 2.x 与 3.x 的现行提案与后续新增。任何方案若靠"多堆一轮验收"来表态严谨，视为违反本条。
- **3.6 时间/token 是唯一被承认的正当成本**：重复的全树扫描、每次执行的全量重哈希、schema 反复回读属于**必要成本之外的浪费**，须按 2.7/§7 消除，不得用"这是流程要求"来正当化。

## BP-4　跨平台同一项目语义（协作原则）

> 一个项目被分成多个 run、在不同平台上跑时，跟在同一个平台上跑一样：**换客户端接着干不需要手工拼装，功能面与版本语义不降级**。**不要求多平台同时开工**（2026-09-22 用户裁决，口语原文见 §9 第 10 条）。

**条文**

- **4.1 等价要求**：同一项目被拆成多个 run、分布在多平台/多会话执行时，使用者得到的**功能面、版本语义与操作方式**，必须与在单一平台上连续执行**等价**：功能不降级、接入与更新轻便。
- **4.2 "无缝"的定义域**（不写兑现不了的承诺）：本文所指等价是 **run 粒度的续跑等价**——一次交接即可在另一平台接着干，零手工拼装，功能面不因换平台缩小，换平台前后钉住的版本一致。**进行中的单个 run 不做在线热迁移**（run 仍是单写者、状态机不搬）。这是设计边界，不是缺口。
- **4.3 续跑必需的两项机制（2026-09-22 由三项裁减为两项，缺一即视为未满足本条）**：
  - **① 续跑版本一致性校验**：续跑前比对目标平台所钉 agent / 工作流 / 依赖 / 软件配方版本与锁内版本；不一致时**明确警告或拒绝**，不得静默换版（承接"解析一次即冻结"不变量，也是 2.0.0 §8 缺陷③ 的封堵点）。
  - **② 可回读的交接载体**：续跑所需的上一阶段结论、产物摘要与项目可写状态，以**带 sha256 与 provenance 的交接包**（现行形态：2.1 的 `handoff-bundle/v1`）或**用户指定的共享项目路径**承载；任何平台不得直读别平台 `runtime/`。**原 4.3① 要求"必须存在一个不属于任何平台的中立状态层目录"这一强制形态自 2026-09-22 撤销**——被撤销的是"必须专门建一个目录"，不是"交接内容必须可回读、必须带哈希"。
- **4.4 并行与跨平台资源仲裁不再是本条的必需项**（2026-09-22 用户裁决）：撤销原 4.4「并行是一等能力 + 共享并行编排模板」、原 4.3③「互斥键须在所有平台之间有效」、原 4.5「中立层目录的创建须用户单独授权」三项。已实现的机制（`handoff-bundle/v1`、续跑不一致即拒、3.0 参考网关的锁表与 `exclusiveResources`）**全部保留**，其作用域如实声明为**同一平台内**，不得写成跨平台有效。**本条明写被接受的代价**：同一项目副本被两个客户端同时开工时，**没有任何机制会发现或阻止，两边会互相覆盖**；分处两台机器的执行同样不提供互斥保护。任何文档、能力声明或收口报告都**不得**把这句话说成"架构已提供跨平台互斥"。
- **4.5 裁减依据（实测，不是推定）**：当前六个"平台"是**同一台机器、同一个 `E:\ai` 文件系统**下的不同客户端，文件互相可见；用户 2026-09-22 自述实测"换客户端继续跑几乎无痛"，故 4.3 两项由人工错开 + 交接包即可满足。**若将来出现真正的分机执行需求**，本条按 BP-5 另立 P 表重新裁定；执行期不得顺手加码，也不得由某平台自行宣布恢复互斥要求。

## BP-5　分步实施与完成判定（执行纪律原则）

> 用户原始表述（口语版）见 §9 第 5–7 条。本条把"给 AI 出方案的要求"升为上位纪律：**方案必须切得开、执行必须照案走、跑完必须算完成。**

**条文**

- **5.1 无 P 表不得进入执行**：任何架构更新、迁移、平台接入、发布或修复方案，在进入执行前必须给出**有序 P 步表**（`P1…Pn`）。没有 P 表的方案只是议题，**不构成实施授权**；执行者有权拒绝按"整块任务"开工。
- **5.2 P 的时限与子块**：单个 P 的预计墙钟时长控制在 **2–3 小时**，超过 3 小时必须再切；每个 P 内部再分 **2–4 个子块**（`P1.1 / P1.2 / …`），每个子块有独立可判定的产出物。**切块的正当理由是人的作息，不是任务的逻辑边界**——一次更新不得因为"程序还在跑"而跨过既定的休息窗口。
- **5.3 每个子块都要有可中断点**：子块结束时必须处于"可安全停手"状态——不留半截写入、不留在途 run、结论与产物已落盘且可回读。预计在该时段收不了尾的子块，**不得排在该时段末尾**。
- **5.4 严格照案执行；非阻断缺陷只登记不即修**：方案批准后一律照案执行，不即兴扩范围、不顺手重构、不中途改设计。执行期新发现的漏洞与偏差，**只要不阻断当前 P 的判据、不违反 §6 红线，一律只做登记**（现象 / 复现条件 / 影响面 / 初步定位 / 建议处置），写入本轮台账与缺口清单，**项目收口后统一出一份修复方案**（另立 P 表）。
  - **当场处置的三类例外**（除此之外一律登记）：① 不处置会造成不可逆损失或破坏已发布版本只读性；② 不处置会违反 §6 红线；③ 不处置则当前 P 的判据根本无法判定。当场处置须在台账标为**越界处置**并写明理由与影响面。
- **5.5 完成判定必须闭合**：**方案全部 P 步按其预先写明的判据执行完毕 ⇒ 该次更新即告完成。**同一轮内**不得**追加新验收项、不得提高判据门槛、不得以"再补一轮更严谨"为由延后宣布完成——**"步骤跑完了但还不算完成"是违规状态，不是谨慎**。
  - **加码的唯一合法时点是方案定稿之前**；定稿后冒出的想法一律进 5.4 的登记面，作为完成后的维护事项另立方案。
- **5.6 完成的定义 = 判据 + 可回读证据**：一个 P 完成，当且仅当其判据满足且产出物可回读（`run-lock.json`、事件流、产物哈希、机检报告等**本来就在写**的东西）。回读既有产物属零额外成本，**不是**新增仪式；缺证据不得宣布完成（§6 红线 3、4）。两句共同成立：既不得用"再加一项验收"拖延完成，也不得用"没跑验收"冒充完成。
- **5.7 登记项的归属**：5.4 登记的缺陷属**完成后的维护期**，独立立项、独立排 P，**既不折抵本项目的完成状态，也不因本项目已完成而被丢弃**；缺口台账须在项目收口时一并交付，逐条可回读。
- **5.8 P 表最小格式**：每行至少含 ① 编号与目标 ② 预计时长 ③ 子块清单（2–4 个）④ 产出物 ⑤ 完成判据（可机械回读）⑥ 前置依赖 ⑦ 中断点。**收尾报告逐行回读该表**，逐行标注"已完成 / 已登记"。

**判据**：方案是否"可执行" = 是否含满足 5.1–5.3 与 5.8 的 P 表；一轮更新是否"完成" = 是否满足 5.5–5.6 且无未归类的当场扩项。

**对既成基线的效力（不撤销事实，只重新归类）**：`架构2.0.0.md` §10 的未完成项按本条重新归类为**完成后的维护 / 补接事项**——不得读作已通过，也不再作为"2.0 更新未完成"的理由；其中**等待型**项目（如 48h 观察窗口）按其性质只能是维护期观察项，**不构成定稿或完成的先决条件**（与 §0.2、BP-3 3.2③ 一致）。

**当前差距（2026-09-19 实测）**：`架构2.1.0-更新方案.md` 全文**没有 P 步表**（本轮补，见其 §9）；2.0 提案 §19 的 `P0–P7 / 30–47 工程日` 与 3.0 提案 §13 的 `P0–P10` 都是**工序序**、不满足 5.2；`平台接入清单.md` 与 `架构2.0.0-恢复手册.md` §5 尚无"执行期不得加码"的对应条款。**→ 属未满足，不得读作已建立纪律。**

## BP-6　入库先行与可回滚（可恢复性原则）

> 用户原始表述（口语版）见 §9 第 8 条。本条的来历是一场**已经发生的事故**：2026-09-19 约 01:25，qoder 的整个接入面（`bridge/` + `runtime/`）被平台更新清空。配置面当天从会话 transcript 还原 91/101 件，而**一手证据（`2.0-C`/`2.0-D` 的 baseline JSON、`pre-adoption/` 逐字节备份、删除前的哈希清单）永久不可回读**。同年另有一例：`codex_backup.zip`（约 40.98 GB）连文件都不在盘上，其文档里的回滚引用失效。

**条文**

- **6.1 入库是收口条件**：任何架构更新、迁移、平台接入、发布或修复，在按 5.5 宣布「P 步跑完即完成」**之前**，必须把本轮产生的**治理文本与平台配置面**提交进根仓 `E:\ai` 的 git。没有提交读数的收口报告不得判为完成（与 5.6 并列，不替代它）。
- **6.2 破坏性动作之前必须先有回滚锚**：重建密封环境、切换指针、清目录、重接平台、搬移或删除既有内容、任何 `git checkout/reset/clean`——一律只能在**已提交的状态**上进行；进不了 git 的部分（见 BP-7）必须先有 inbox 备份登记。**先入库、后动手**是顺序要求，不是收尾礼仪。
- **6.3 入库面由白名单定义，不由临场判断**：入仓 = 治理文本（根级 `*.md` + `versions/`）+ 三共享仓 + 各平台 `bridge/` 接入面文本层；**不入仓** = `runtime/` 运行产物、凭据、缓存、日志、软件本体、密封脚本环境（那些走 BP-7）。白名单自身是文本，改动随提交进历史。
- **6.4 推送与可见性**：提交后推送到治理远端（当前 `origin`）。**推送前必须过凭据 / 本体 / 超限大文件红线扫描，命中即停**；含凭据的文件、软件本体、白名单外的二进制一律不得出库。禁止对已有历史 `force push`；无共同祖先的导出仓不得强推（实测两枚 `1.0.0` 导出仓即属此类，不得为「传上去」而改写对方历史）。本条的推送授权由用户 2026-09-20 深夜的指令确立（§9 第 8 条），但**首次启用时须向用户确认远端与可见性**，之后按本条常规执行。
- **6.5 一次更新一个可寻址回滚点**：收口报告必须写明「要撤销本轮，回到哪个 sha」。写不出这个 sha，就说明本轮改动不具备可回滚性，只能按 5.4 登记为未完成，不得宣布完成。

**判据（可机械回读，单条命令出 pass/fail）**

1. `git -C E:/ai rev-parse HEAD` 有值，且该 sha 写进本轮收口报告；
2. `git -C E:/ai status --porcelain` 在**白名单内为空**；白名单外（各平台 `runtime/` 等）不要求为空，但其归属须逐条列出，不得留作未解释的脏项；
3. `git -C E:/ai ls-remote origin` 的目标分支与本地 HEAD 一致（证明「上传」确实发生，而不只是本地提交）；
4. 本轮涉及的每个配置件，其**最近一次入库时间 ≤ 该件被破坏性改动的时间**（回读 `git log -1 --format=%cd -- <路径>`）。

**不做**：为了「满足本条」把 `runtime/`、凭据或本体塞进 git（那是拿红线换判据）；用「以后再提」抵充 6.2；把别会话的未收口改动混进本轮提交（脏项须逐条归属，说不清就不提）。

## BP-7　不可入库件的隔离与备份（副本原则）

> 用户原始表述（口语版）见 §9 第 9 条。BP-6 管「能进 git 的那一半」，本条管**进不去的那一半**——venv、WSL 密封脚本环境、软件本体、真机产生过的数据目录、大缓存。它们恰恰是重建代价最高、最容易在一次平台更新里陪葬的东西。

**条文**

- **7.1 定义**：不可入库件 = 因体积、二进制形态、许可或凭据原因不得进治理仓的内容。判「能不能入库」按 6.3 的白名单，不按文件类型的感觉。
- **7.2 平台隔离**：这类件必须落在**所属平台目录内**（`<platform>/runtime/…`）。不得放根级、不得跨平台共享同一份、不得在共享代码/契约/配方里出现其绝对路径（同 2.5）。判据是一句可检验的话：**任何一台平台的这类件坏掉，不得波及其他平台。**
- **7.3 备份区固定在 inbox**：落点 `inbox/backup/<platform>/<对象>-<YYYYMMDD>/`。每份备份必含：对象说明与来源、**逐文件 sha256 清单**、体积、**重建命令**、实测重建耗时、是否含凭据；同时在 `inbox/_inventory/` 台账登记一行。
- **7.4 两档备份要求（判据不同，不得混用）**
  - **可重建件**（venv / 密封脚本环境 / 解包产物）：必须交「**重建配方 + 校验和 + 一条可重放的重建命令 + 重建后 selftest**」。**裸副本不是必需的**——一份会漂移的副本不如一个能重放的配方；但**缺配方即视为未备份**。
  - **不可重建件**（真机产生过的数据目录、用户手工移植物、无源的下载物、含凭据的现役配置）：**必须留完整副本**，并按 7.6 标注凭据边界。
- **7.5 恢复演练才算数**：新登记的备份必须做过**至少一次真实恢复**（在隔离目标上重建 → 校验 sha256 → selftest 绿）并留读数。**没演练过的备份按未备份处理**（红线 4：不得把「应该有」写成「已完成」）。
- **7.6 凭据边界**：含凭据的备份必须显式标注，不得入 git、不得随仓分发或打包导出；明文口令一律不落任何文本（既有口径：只记偏移 / 长度 / 形状 + 源文件哈希）。
- **7.7 inbox 的三区职责**（本条同时确立 `inbox` 的角色，细则见 `inbox/README.md`）：
  - `inbox/backup/` —— 按平台隔离的不可入库件备份（7.3 的落点）；
  - `inbox/archive/` —— 已被治理文档引用、不再工作但必须可回读的历史件。**归档若移动路径，必须同步改引用或在原位留指针**，否则违反红线 3（provenance 可回读）；
  - `inbox/trash/` —— 待清理区。**垃圾桶不是删除器**：入区只登记，清空须用户**逐批**授权。`inbox` 的旧规则原样有效：不自动发现、不自动执行、不自动删除。

**判据**：对每个已声明的不可入库件，`inbox/backup/<platform>/…` 下有 MANIFEST 且 sha256 可对上；7.4 第一档另须有「重建 → selftest 绿」的读数；`trash/` 的任何清空动作有逐批授权记录。做不到其中任一项，该平台不得声称「环境可恢复」。

**与 BP-1 / BP-6 的关系**：本条不改变「本体、凭据、运行产物不入共享仓」（1.3）；它给这些内容一个**有主、可恢复**的去处，从而让 BP-6 的「入库先行」不会因为「反正进不去 git」而整段落空。

## 5. 原则互相冲突时的裁定顺序

1. **BP-4 vs「产物归平台」（2.0.0 §2 不变量 3 / 系统提示词 §二）**：按**内容类型划界**，不是谁整体让位。
   - **归平台**：平台配置、凭据、缓存、日志、run 私有一手证据、本体安装位、**网关的平台内锁表**（2026-09-22 起跨平台仲裁不再是必需项，锁表留在平台内即为正确形态）。
   - **必须可跨平台读回**（经 4.3② 的交接载体，不直读别平台 `runtime/`）：续跑所需的项目可写状态、跨 run 版本锁、已完成阶段的结论与产物摘要。
   - 扩写后的不变量口径：**「运行*私有*产物只写本平台目录；被声明为*项目状态*的内容以带哈希的交接包或用户指定路径承载，其他平台只经交接接口访问它。」** 平台隔离不被废除，只是不再覆盖项目状态这一类。
2. **BP-3 vs BP-2**：地板不因"贵"而放弃（功能可用是硬要求）；但**认证方式**必须最小。二者同时成立的路径是"一次做到、增量维护"，不是"少做以省事"。
3. **BP-2 vs 平台自治（选版自决）**：版本可以各平台自钉、不得替他人升版；但**能力面目标唯一**。长期钉旧版导致功能面小于并集，属 2.4 的待补项，不是合法差异。
4. **BP-1 优先于一切实现便利**：任何做法若要求破坏三仓骨架或改写已发布版本，直接否决。
5. **BP-5 vs BP-3（管的东西不同，不得互借）**：BP-3 管**验收深度与成本**（别把检查做重），BP-5 管**实施切块与完成判定**（别把方案做成不可切分、别在完成判定上加码）。不得用 BP-5 的"跑完就算完成"去削减 BP-3 必留的四项检查，也不得用 BP-3 的"要增量"去拒绝 BP-5 的时限切块。
6. **BP-5 vs §6 红线（5.5 不是免检牌）**：完成判定闭合**不覆盖**红线 3、4（证据可回读、不得谎报）。红线项没做到就是没做到，只能按 5.4 记为"已登记 / 未完成"，不得由 5.5 判成"已完成"。
7. 仍无法裁定时：**停下问用户**。不得自行放宽 §6 红线来"解决"冲突。
8. **BP-6 / BP-7 vs BP-3（成本）**：入库与备份是**必要成本**，不受最小量削减。BP-3 能削的是重复副本的数量与验收轮次，**不能削「有没有回滚点」**；7.4 用「重建配方」替代裸副本，正是两条同时成立的解法。
9. **BP-6 vs 红线 5 / 红线 8**：向 `E:\ai` 治理仓提交属本平台留痕，不构成共享仓写入；但 `push` 是**对外可见**动作，其授权由用户 2026-09-20 深夜的指令确立（§9 第 8 条），首次启用前向用户确认远端与可见性，推送前必过凭据 / 本体扫描。**不得用「要入库」去换 1.3 / 6.3 的「本体与凭据不入仓」——入库面是白名单，不是能塞就塞。**

## 6. 红线（不因最小量、对等或无缝而削减）

1. 已发布版本只读、不可变；换版=新目录 + 翻指针。
2. 任何 run 固定版本并写 `run-lock.json`；**快速档也要写薄锁**。
3. 完整性哈希与 provenance 可回读；缓存/降级**不得掩盖版本漂移或篡改**，须保留"每 run 至少一次权威校验"。
4. 不得谎报：`prepared` / `gated:false` / 快速档 / 未实测，一律不得写成已完成、已验证、已冻结、已接入。**未达交稿档不得称已验证或已冻结**（原"非交稿"表述，2026-09-22 起对全部工作流通用）。
5. 未经用户授权：不写共享仓、不改他平台目录、不建新一级目录、不切共享 `current`。
6. **档位口径对所有工作流统一生效**（2026-09-22 由"数模专属"通用化，原条文见下）：未声明档位＝**最低档**，只做点名范围——不 INIT 已有项目、不重跑求解器/扫描、不扫参、不额外独立验证、不过严图、不冻结；写「过图」才跑非严格 QA；写「交稿」才走该流程声明的全部阶段并冻结。禁止用 runner INIT 清空已有项目。**数模自本日起不再有专属链路、专属环境或"交稿须转某平台"式的跨平台特例**，与任何 agentic workflow 等同；其环境需求按 **1.6** 的三条路之一归属并写明。引擎侧 `rigor` 三档与已发布的数模工作流 / 专家字节**一字未动**（红线 1），被取消的只是治理文本里的特殊地位。
7. 降到主机执行的降级路径必须**当次同意 + 入锁留痕**，不作为静默默认。
8. 三仓只读、平台间不互改配置/状态/工作区（项目状态按 §5.1 划界）。
9. **可恢复性红线**：配置面与治理文本在破坏性动作之前必须已入库（BP-6）；不可入库件必须有可恢复的 inbox 备份登记且演练过（BP-7）。二者缺一，该轮不得宣布完成。
