# 架构 3.4.0：独立架构管理台方案

> 版本：**3.4.0（方案稿）**
> 日期：**2026-09-25**
> 前置基线：`versions/架构3.3.0` 当前工作树、`versions/架构基本原则.md` BP-1～BP-7、3.2.0 软件连接器方案
> 配套实施表：`versions/架构3.4.0-独立架构管理台定稿实施表-20260925.md`
> 本文性质：**独立用户版管理工具的目标架构、边界和完成判据**。P0–P9 已按配套实施表完成，收口基线见 `versions/架构3.4.0.md`。

## 1. 这次要解决的问题

目前架构的治理内容、平台配置、三仓版本、软件配方、运行台账和 Git 状态分布在多个目录。熟悉规则的人可以通过文件和命令管理，新用户却很难判断：

- 哪些平台已经接入、哪些只是登记项；
- 某个 skill、agent 或 workflow 当前到底使用哪一版；
- 一个更新计划做到哪一步，哪些判据已经通过；
- 软件本体在哪里、配方是否冻结、能不能调用；
- 当前 Git 是否干净、哪个版本可以回滚、哪些改动尚未备份。

3.4.0 建立一个**每个用户独立使用的架构管理台**。它把现有文件、版本指针和维护记录变成图形化的查询、规划、执行和回读界面，使新用户可以双击打开、按页面操作，不需要先掌握 PowerShell、Git 或目录规则。

## 2. 用户和部署边界

### 2.1 一人一套架构副本

每个人拥有自己的架构目录、自己的 Git 仓库、自己的软件本体和自己的运行状态。用户之间不共享：

- `tool`、`agent`、`software` 的本地副本；
- 平台配置、runtime、日志、缓存和凭据；
- 软件安装目录和解释器；
- 维护计划的执行证据；
- GitHub 账号、令牌和远端仓库。

3.4.0 **不建立中心服务器、不建立多人账号、不建立共享数据库、不把任何用户的 runtime 上传给其他用户**。将来若需要协作，可以另立版本方案，不能把本方案的单机状态解释成多人同步。

### 2.2 目录可配置

`E:\ai` 是当前用户的默认工作区，不是程序内置的唯一路径。首次启动时用户选择架构根目录，程序记录工作区 ID 和路径映射。程序必须识别现有正式一级目录，不擅自创建新的 E:\ai 一级目录。

管理台程序源代码和安装文件放在架构工作区之外；架构工作区只保存它本来就应保存的治理文本、平台状态和运行证据。管理台的界面缓存、窗口设置和操作索引放在用户本机的应用数据目录，不污染三仓和平台 runtime。

### 2.3 两种本地发行方式

| 发行方式 | 适用人群 | 行为 |
|---|---|---|
| 安装版 EXE | 日常使用 | 安装到系统目录，双击启动，可创建开始菜单快捷方式 |
| 便携版 EXE | U 盘、临时电脑或不想安装的用户 | 解压后直接运行，工作区路径由用户选择 |

两种发行方式使用同一套 HTML 界面、API 和验证逻辑。管理台默认只监听 `127.0.0.1`，不开放局域网端口。

## 3. 目标架构

```text
┌──────────────────────────────────────────────┐
│ 架构管理台.exe                               │
│                                              │
│  React/TypeScript HTML 界面                  │
│        │                                     │
│  受限 preload API / 本地管理 API             │
│        │                                     │
│  文件读取与写入计划 · Git 适配器             │
│  三仓版本解析 · conform 调用                 │
│  软件连接器 / 会话控制                       │
└────────┬─────────────────────────────────────┘
         │ 仅访问用户选择的工作区和已登记路径
         ▼
┌──────────────────────────────────────────────┐
│ 用户自己的架构工作区                         │
│ tool · agent · software · 各平台 · versions  │
│ inbox · runtime · Git 工作树                  │
└────────┬─────────────────────────────────────┘
         │ 仅通过已登记 recipe/provider
         ▼
┌──────────────────────────────────────────────┐
│ 用户本机软件、解释器、Git 和 GitHub 凭据      │
└──────────────────────────────────────────────┘
```

### 3.1 技术选择

- **桌面壳**：Electron。现有架构大量使用 Node.js 和 `.mjs`，Electron 可以复用解析器、Git 适配器和现有脚本，并提供 Windows 双击启动能力。
- **界面**：React + TypeScript + HTML/CSS。界面组件采用清晰的表格、状态徽章、向导和差异视图，避免用户直接编辑 JSON。
- **本地 API**：Electron 主进程和 preload 暴露的类型化 API。渲染层不能直接获得 Node 文件系统、进程或 shell 权限。
- **数据读取**：优先读取现有 `registry.json`、`current.json`、manifest、`SHA256SUMS`、平台 bridge/config、维护台账和 Git 状态；不复制一份会与原文漂移的“第二真相”。
- **操作记录**：应用数据目录保存 UI 状态和操作索引；需要留在架构内的维护证据写入所属平台的 `runtime/maintenance` 或用户明确选择的 `inbox/archive`，不写入发布目录。
- **Git 操作**：使用参数数组调用已检测到的 Git 可执行文件，禁止 `shell=true` 和任意命令输入；没有 Git 时只提供只读盘点和安装引导。

### 3.2 三层操作模型

所有写操作都经过三层，不允许按钮直接改文件：

1. **查看**：只读扫描，展示来源路径、版本、哈希、状态和证据链接。
2. **计划**：把用户选择转换成带文件清单、旧值、新值、备份点、预期验证和回滚入口的 plan；用户可以导出和审阅。
3. **执行**：用户确认后按 plan 执行，写入 checkpoint、事件、产物哈希；执行后自动回读并显示验证结果。

执行失败必须保留诊断文件，并提供按 checkpoint 回滚。旧版本目录、已发布字节和历史证据不由界面删除或覆盖。

## 4. 图形化功能范围

### 4.1 首页与工作区

首页显示：

- 当前工作区路径和工作区 ID；
- 架构基线版本与管理台版本，二者分开显示；
- 平台数量、三仓资源数量、软件数量；
- 当前指针是否与 manifest/SHA256SUMS 一致；
- Git 分支、未提交文件、未推送提交和远端差异；
- 最近 P 表、最近失败、待处理的 `declaredAbsent`/`unverified`；
- “只读扫描”“生成计划”“打开工作区”“导出报告”入口。

首次启动默认只读扫描。扫描完成前不提供批量写入按钮。

### 4.2 平台管理

平台列表读取现有平台目录和 bridge/config，按以下状态分开：

- 已接入并有独立证据；
- 已登记但未完成接入；
- 已停用或仅作历史登记；
- 目录存在但来源和用途不明。

用户可以：

- 添加平台登记：填写平台 ID、显示名称、根目录、bridge 路径和接入状态；
- 启用或排除平台：默认只改变本地管理视图；若要改变正式配置，必须生成计划；
- 运行平台只读 self-check 和单格 conform；
- 打开平台章、最近维护台账和 runtime 目录；
- 比较两个平台自己的配置差异。

“排除”默认是可恢复的停用标记，不删除平台目录、配置、日志或证据。跨平台结论仍遵循 BP-2，不能因为管理台把某平台隐藏就声称它已经接入。

### 4.3 skill、agent 和 workflow 管理

资源页面从三仓 registry 和 current 指针计算当前状态，显示：

- ID、显示名称、当前版本、可用版本；
- manifest、提示词、tool-lock、依赖、能力包和技能快照；
- 发布哈希、只读状态、引用它的 agent/workflow；
- 各平台解析到的版本来源；
- 最近 conform 和单格冒烟结果。

新增或更新向导分为：

1. 选择资源类型和 ID，检查版本目录不能已存在；
2. 从模板生成新 semver 目录和 manifest；
3. 编辑提示词、tool-lock、schema 或技能声明；
4. 运行结构校验、依赖闭包和 SHA256 双向校验；
5. 展示 plan/diff；
6. 发布新版本或只保留 staging；
7. 按用户选择切换本地 current，并回读验证。

“删除”按钮不物理删除已发布版本，只提供“停用/撤销默认指针/归档候选版本”。已发布版本目录保持只读。

### 4.4 更新计划、文档和顶层要求

计划中心按 P 表管理：

- 方案稿、定稿实施表、维护台账、收口报告；
- P 步状态：未开始、进行中、已安全停手、通过、登记缺陷、阻断；
- 每个 P 的判据、产物路径、哈希、执行时间和责任平台；
- 计划与实际 Git 提交、runtime 证据的关联。

文档中心支持：

- Markdown 预览和编辑；
- 来源路径、当前版本和 Git 差异；
- 版本化保存和回滚；
- 文档站构建、断链检查和排版检查；
- 将计划、台账和架构基线导出为 HTML/PDF。

`versions/架构基本原则.md`、当前架构基线和平台接入清单属于高敏感治理文本。编辑前必须显示影响面、引用它的文件和回滚点；不能通过普通“快速保存”绕过计划层。

### 4.5 软件中心

软件中心区分四件事：配方、能力快照、本体安装、连接器状态。每行显示：

- 软件 ID、配方版本和 current 指针；
- 本机实际路径、解释器、上游版本和本体哈希；
- 快照是否冻结；
- `software.list/describe/health` 结果；
- 可用操作、授权要求、会话模型和独占资源；
- 最近成功调用、失败原因和证据路径。

软件接入向导收集：

1. 软件名称、ID、上游版本和本体位置；
2. 类型：CLI、原生 MCP、HTTP、GUI/长会话；
3. recipe、输入输出 schema、能力快照和 selftest；
4. interpreter/profile、项目写入根、网络和凭据引用；
5. `generic-cli`、`mcp-proxy` 或 `desktop-session` adapter；
6. 只读测试和拒绝测试；
7. 发布、回读和本地启用计划。

每个软件不单独重写一套 MCP。默认复用共享连接器和通用 adapter；只有协议确实独立时才登记薄适配器。软件本体和真实凭据不进入 Git。

“启动软件”按钮只调用已登记的 recipe/provider，展示目标路径、版本、权限和预期副作用后再执行。GUI 软件可返回 `INTERACTIVE_REQUIRED`，不能把“窗口已弹出”伪装成业务调用成功。

### 4.6 Git、GitHub、备份和回滚

Git 页面分为四个视图：

- **工作树**：当前分支、修改、未跟踪文件、敏感文件扫描；
- **版本**：提交、标签、架构基线、资源版本和指针变更；
- **远端**：远端 URL、领先/落后、待推送提交、GitHub 登录状态；
- **恢复**：备份点、checkpoint、可回滚提交和恢复预览。

常用操作：

- 初始化或绑定个人 Git 仓库；
- 生成提交说明和变更摘要；
- 提交前扫描凭据、本体、大文件和被忽略目录；
- 拉取、创建分支、提交、推送和创建标签；
- 从指定提交生成回滚计划；
- 预览恢复影响，确认后生成安全回滚提交；
- 导出离线备份和 `SHA256SUMS`。

程序不自动强推、不默认删除远端分支、不执行 `reset --hard`。GitHub 凭据使用系统凭据管理器或 Git Credential Manager，不写入架构目录、日志、plan 或证据。

## 5. 数据归属和安全边界

| 内容 | 存放位置 | 管理台处理方式 |
|---|---|---|
| 共享治理文本 | 用户自己的 `tool/agent/software/versions` | 读取、生成计划、校验、提交 |
| 平台配置与 runtime | 对应平台目录 | 只访问本平台，显示和按计划变更 |
| 软件本体 | 平台 `runtime/software` 或用户登记位置 | 读取版本、路径、健康状态，按 recipe 启动 |
| 凭据 | Windows 凭据管理器或平台指定密钥环 | 只使用 reference，不读出真实值 |
| 管理台缓存 | `%LOCALAPPDATA%\ArchitectureManager` | 不进入架构 Git |
| 审计与维护证据 | 所属平台 `runtime/maintenance` 或明确的 archive | 记录 plan、事件、哈希和结果 |
| GitHub token | Git Credential Manager/系统凭据 | 页面只显示已登录、未登录或失效 |

主进程必须使用 `shell:false`、参数数组、路径规范化和允许根检查。渲染层使用 `contextIsolation`，不启用 `nodeIntegration`。所有写入先检查工作区锁、文件哈希和版本是否仍匹配；发现外部改动即停止并要求重新生成 plan。

## 6. 与现有架构的关系

1. 不修改 BP-1～BP-7。
2. 不新建第二套 tool/agent/software 仓库。
3. 不把管理台本身当成 workflow、agent 或 software 配方。
4. 不把管理台的 UI 状态写入共享发布目录。
5. 不改变已发布资源，只通过新版本目录和 current 计划更新。
6. 不替代现有 `conform`、run-lock、handoff-bundle 或平台证据；管理台只把它们可视化并按已登记入口调用。
7. 不宣称提供跨用户同步、跨机器互斥或远程执行。
8. 3.3.0 的 skill/agent 更新和 3.4.0 的管理台更新分开收口。

## 7. 完成后的用户体验

新用户拿到安装包后：

1. 双击启动管理台；
2. 选择自己的架构根目录；
3. 等待只读扫描结束；
4. 首页看到平台、资源、软件和 Git 状态；
5. 按向导添加或停用平台、skill、agent 和软件；
6. 在计划页查看每个文件将如何变化；
7. 点击确认执行，程序自动备份、校验、提交或回滚；
8. 在软件中心直接检查或启动本机软件；
9. 在版本页区分管理台版本、架构基线版本和资源版本。

用户不需要知道 JSON 字段、命令行参数或 Git 命令；高级用户仍可打开来源文件和完整 diff。

## 8. 3.4.0 的完成判定

只有配套 P 表全部通过，才宣布 3.4.0 完成。至少必须满足：

1. 安装版和便携版都能在无控制台窗口的情况下启动，并打开本地 HTML 管理界面；
2. 首次扫描不修改工作区，能正确读出三仓、平台、版本、软件和 Git 状态；
3. 平台启用/排除、资源版本管理、文档计划和软件登记都经过 plan→apply→verify；
4. 已发布版本不被覆盖，删除操作只产生停用或回滚计划；
5. 至少一个 CLI、一个 GUI 或会话型软件通过已登记 connector/provider 完成健康检查或真实启动/关闭；
6. Git 提交、差异、备份、回滚和个人 GitHub 推送状态在界面可读；
7. 凭据、本体、缓存和 runtime 不进入 Git，敏感文件扫描能阻断误提交；
8. 外部改动、哈希不一致、路径越界和未授权操作都在写入前阻断；
9. 所有 P 产物、测试摘要、版本哈希和收口读数可回读；
10. 收口提交包含 HEAD、白名单内 `git status`、远端一致性和入库时间。

## 9. 不在本轮范围内的内容

- 中心服务器、多人账户、组织和角色系统；
- 用户之间的仓库共享或实时同步；
- 云端运行软件和远程控制用户桌面；
- 自动替用户决定是否推送 GitHub；
- 替换现有三仓、平台 bridge 或 3.2.0 连接器契约；
- 自动删除平台目录、旧版本、日志、缓存或软件本体；
- 把所有 GUI 软件强行改造成 MCP；
- 在没有真实端点或能力快照时刷绿软件状态。

详细执行顺序、每步时长和判据见配套 P 表。
