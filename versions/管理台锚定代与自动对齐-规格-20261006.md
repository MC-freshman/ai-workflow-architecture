## 一、目标与验收（把"全自动"翻译成可判定的东西）

**目标形状**：管理台里有一个**锚定代**（一份机读的"本轮该用哪些版本"的表），点一次就能把任一平台——或全部平台——的**版本面**对齐到锚定代，然后自动跑该平台自己的验证并给出可回读读数。用户只需要看结果与确认，不需要逐个手改绝对路径。

**四条验收（缺一不算达成）**：

| # | 判据 | 可回读证据 |
|---|---|---|
| A1 | 锚定代是一份机读文件，且管理台报告的"锚定代"与它逐字一致 | `versions/锚定代.json`（暂定名）+ 报告 digest |
| A2 | 对任一平台执行对齐＝**一个事务**写完全部版本键，取消即零写入 | plan → apply → 回读；`events.jsonl` + checkpoint |
| A3 | 对齐后自动跑**该平台自己**的 conform + 受影响矩阵格，出 digest | `runtime/manager-check/<stamp>/check.json` + `conform.json` + `matrix.json` |
| A4 | 对齐前后，**其它平台字节零变化**；共享三仓字节零变化 | 对齐前后各取一次四键读数（根因文档 §9.1 V8–V10）逐字比对 |

## 三、锚定代：定义、生成规则、落点

### 3.1 定义（暂定文件，schema 待你定名）

锚定代 = **一组经过配对校验的版本**，覆盖四个轴 + 软件面：

| 轴 | 键 | 取值来源（本轮的锚定候选） |
|---|---|---|
| 引擎 | `wf-runner` | `0.12.2`（其 manifest 自述 repo-lint `0.6.5`） |
| 契约 | `runtime-contracts` | `1.5.2` |
| 检查器 | `repo-lint` | `0.6.5`（= 引擎自述要求，且是 U-01 纠正后的正确身份） |
| 判据 | `architecture-ops` | `1.5.2`（`invocationSmoke` 接口齐备）；一致性判据另用 `platform-conformance` `1.5.1`（已发布最新） |
| 软件面 | `software` 八件 + 每平台绑定 | `_connector 1.0.7`、`_gateway 1.0.1`、六配方各自 `current` |

**为什么是这套**：它是**唯一一套同时满足三个约束**的组合 —— ① 引擎自述的 repo-lint 与之相等（`0.12.2` ↔ `0.6.5`）；② 判据包带 `x-invocationSmoke`（`0.12.2` 的 smoke 接口才可用）；③ 已封存且有发布溯源（P7 记录 `架构管理台统一实施P7记录-20261003.md:5`）。**这就是 dsh 现在那一套。**

### 3.2 生成规则（关键：不盲拼"最新"）

```
anchor(轴) = 就绪集合 ∩ 配对闭包 ∩ 最新
  就绪集合   = 该资源已发布版本（versions/<v>/ 存在且 SHA256SUMS 双向可验）
  配对闭包   = 引擎 manifest 自述的 repo-lint == 所选检查器；判据 manifest 带 invocationSmoke
  最新       = 语义化最大，仅在闭包内比较
```

生成时必须**逐条报出候选为什么落选**（例：`wf-runner 0.12.1` 落选 —— 自述 `0.6.4`，与检查器最新 `0.6.5` 不配对）。管理台已有同一原则的书面依据：**"新平台推荐组合由当前冻结 manifest/依赖配对决定，不能取三个『最新』字符串盲拼"**（`架构管理台全面修复模块化接入与提速方案P表-20261003.md:112`）。本规格只是把它变成**可回读的锚定件**。

### 3.3 落点（两案，待你裁定）

| 案 | 落点 | 优点 | 代价 |
|---|---|---|---|
| **甲案（推荐）** | 工作区单文件 `versions/锚定代.json`（与既有 `versions/` 治理文本同区） | 一处定义、六平台与报告共读；改锚是显式动作、可 diff、可评审 | 需在管理台加读写该文件的 plan；`versions/` 属治理文本区，写入要有你自己的提交习惯 |
| **乙案** | 管理台仓内 `src/domains/.../anchor.json` + 出包时冻结 | 不动工作区 | 改锚＝改代码＝出包；六平台无法直接读，可回读性弱 |

> 注：**不宜**把锚定代写进 `tool/` 共享仓 —— 那属共享字节写入，须单独授权（本轮明写不做）。

### 3.4 与"共享 current"的关系（必须写清，否则又会缠回原问题）

- 锚定代是**管理台的建议/执行目标**；共享 `current.json` 是**矩阵与引擎的默认回落值**。
- 两者**可以不同**（当前就是：锚 `0.12.2/0.6.5`，共享 `0.12.0/0.6.3`），这正是"平台可领先/落后于共享"的合法空间。
- 因此锚定操作**不翻共享指针**；报告里必须同时显示"与锚定代的差"和"与共享的差"两列（后者可能是合法的采纳时差）。

## 四、一键对齐事务：操作定义

### 4.1 计划（plan）

- plan kind：`align-platform-anchor`
- `target`：`{platformId, anchorId, anchorSha256}`（锚定件的内容哈希进计划，避免"计划生成后锚变了"）
- `writePerformed:false`、`applyMode:'confirmation-required'`（沿用内核门）
- **预览必须逐文件列出**将改的键与将写的值（老值 → 新值），以及"哪些键不动"

### 4.2 写入范围（一个事务内）

| 文件 | 键 |
|---|---|
| `<platform>/bridge.json` | `runner.version`、`runner.release`、`defaults.workflowVersions['repo-lint']` |
| `<platform>/bridge/<id>-config.json` | `runner`、`contracts`、`scannerRelease`、`invocationMatrixRelease`；`softwareRoot`、`softwareGateway`、`softwareGatewayConfig`、`softwareEnvironment`、`softwareRuntimeRoot`（缺失则补，存在则指向锚定件的连接器版本） |
| （**不写**） | `bridge.json` 的 `defaults.agentVersions` 等其它键、`capabilities.json`、任何 `runtime/` 内产物 |

**同一事务内必须做的五道复验**（任一不过即整体回滚）：

1. 锚定件的 `anchorSha256` 与计划里的一致；
2. 四个轴路径存在且 `manifest.json` 与 `SHA256SUMS` 双向可验；
3. 引擎自述的 repo-lint == 写入的 `scannerRelease` 版本（**这条仍要查，只是不再阻断** —— 查不过就写警示，不拦）；
4. 回读：原子写后重新读取三个文件，逐键比对；
5. 回滚演练判据：任何一步失败时目录逐字节还原（用内核既有 checkpoint 机制）。

### 4.3 对齐后的自动验证（承接 A3）

1. 调 `runPlatformCheck({mode:'quick', only:null})` —— 版本变了，增量选择器会自行算出**受影响格**（`selection.mjs` 已有 generation/rules 变更判据）；
2. 出 `conform.json`（能力地板）、`matrix.json`（受影响格）、`check.json`（汇总）；
3. 若 `firstCertification` 为空且本次 `fail==0`，则**固化首次认证**并调 `scripts/verify-onboarding.mjs` 出 digest；
4. 报告把这些路径与 sha256 一起写进平台的接入记录（`state.json`）与治理登记（`onboarding-governance.mjs` 的五件文本）。

**边界**：本操作**只跑该平台自己的** conform/矩阵；它**不代其它平台出证**（BP-2 结论不互抄），也**不把旧证据当新结论**。

## 五、批量面：一次对齐全部平台

- 新面板/操作：`align-all-platforms`
- 行为：按平台顺序（codex / dsh / zcode / qoder / workbuddy / doubao）逐平台生成对齐 plan → 用户**一次确认** → 逐平台 apply → 逐平台验证 → 汇总一张表：

| 平台 | 对齐前四键 | 对齐后四键 | 配对 | 平台自己的 conform digest | 矩阵 | firstCertification | 结果 |
|---|---|---|---|---|---|---|---|

- **停止条件**：任一平台失败即停在该平台（不做"带伤继续"），并给出该平台的回滚状态；
- **并行度**：默认串行（六家的 runtime 互不相干，但矩阵会各写自己的 `runtime/`，串行最省心；如需并行，按平台隔离即可，但属另一轮优化）；
- **不做**：不代任何平台声明能力、不替任何平台跑业务 run、不写共享三仓。

## 六、自动化边界：哪些能全自动，哪些不能（必须先对齐预期）

| 面 | 能自动到什么程度 | 为什么 |
|---|---|---|
| 四轴版本键（引擎/契约/检查器/判据） | **全自动**（一个事务 + 回读） | 钥匙与路径都在同一工作区、可校验 |
| 平台默认 `repo-lint` | **全自动**（与 scannerRelease 同批写） | 同一事务 |
| conform + 受影响矩阵格 + firstCertification + digest | **全自动** | 执行器已存在（`platform-check.mjs`） |
| 软件**配方版本**（共享 `software/*/current.json` 消费哪个版） | **自动对齐/上报** | 只读共享指针 |
| 软件**连接器与网关**（`softwareGateway` 指向 `_connector 1.0.7`） | **自动写键**；但**连接器文件是否存在**要看平台 runtime 里有没有那件（管理台能检出并报缺） | 键可写，字节要平台自己装 |
| 软件**本体**（`bodies` 指向的真程序） | **不能全自动**（见下） | 配方**不发行本体**（BP-1：仓内只放配方文本）；本体必须来自**用户指定的安装源**，由 `software-body.mjs` 导入、装进 `<platform>/runtime/software/<id>/`、逐文件哈希入配方 |
| 跨平台出证 | **不能代做** | BP-2：结论不互抄 |

**软件本体的三条现实障碍（实读证据）**：

1. **四平台现存绑定指向外部安装**：codex / zcode / qoder / workbuddy 的 gateway `bodies` 指向 `<local-tool-body-path> `install.location` 写的是 `${platformRuntime}/software/<id>` —— 两者不符；
2. **`bodies` 是标量路径**（`connector.value.bodies[id]` 直接当路径用，`actions.mjs:18`），平台绑定的"版本"只体现在共享 `software/*/current.json` 的指针上，不在 gateway 里；判"是否真绑上"靠**路径对应的文件 sha256 是否等于配方 `verify.files` 里的哈希**（`actions.mjs:20-21`）；
3. **本轮未验证**：我没有对那四个外部路径的文件算哈希、没比对配方哈希（那要逐件哈希大二进制）。所以现在**不能声称**它们"已按配方绑定"，只能说"路径存在、形态是旧标量、与配方声明的 install.location 不符"。

因此软件面的自动化建议分两层：

- **层 1（自动，本轮可做）**：把六件的"绑定状态"做成只读判定 —— 对每个平台每件算 `bodyPath` 是否存在 + `sha256(body)` 是否等于配方 `verify.files` 对应行 ⇒ 三态报告：**配方验证通过 / 存在但哈希不符 / 未绑定**。
- **层 2（半自动，需你选源）**：对"未绑定/不符"的件，走既有 `software-body` 导入流程：**你指定安装源路径**（安装包或已装目录）→ 管理台导入、装到平台 runtime、生成配方与快照、登记共享仓、写真调用探针。这一步**必须有人给源**（配方里没有字节，也不该有）。

## 七、P 步表（**待批准；未批准不构成实施授权**，BP-5）

> 每个 P 控制在 2–3 h 墙钟、可安全停手。**P1 完成即可让你"一键对齐任一平台"**；批量化与软件面在其后。

### P1｜锚定件 + 单平台一键对齐（本次建议先做，约 2–3 h）

- P1.1 新增锚定件与生成器：按 §3.2 的三条规则算锚定代，**逐轴报落选理由**；落点按 §3.3 甲/乙案裁定。判据：对当前盘面算出 `wf-runner 0.12.2 / runtime-contracts 1.5.2 / repo-lint 0.6.5 / architecture-ops 1.5.2`，且能复算出为什么 `0.12.1`、`0.12.0`、`0.6.4` 落选。
- P1.2 预检语义按裁定落地：`onboarding-config.mjs:82-83` 由"抛错阻断"改为"具名警告 + 写入 `journal`/`state.json`/治理登记"，并保留原错误码作为**记录字段**。判据：对 codex 的组合（`0.12.0` + scanner `0.6.3`）能生成计划且带警告，不再抛 `VERSION_PAIR_MISMATCH`。
- P1.3 新增 plan kind `align-platform-anchor`（§4.2 写入范围 + 五道复验）。判据：对 **dsh**（已是锚定代）执行 ⇒ 计划显示"零变更"；对 **codex** 执行 ⇒ 计划列出 6 个键的老值→新值；取消 ⇒ 零写入；apply ⇒ 回读逐键一致。
- P1.4 对齐后自动验证（§4.3）。判据：codex 对齐后自动跑出 conform + 受影响格矩阵，`check.json` 可回读；**同时验证其它五个平台四键逐字未变**（A4）。
- **本 P 不含**：批量面、软件本体导入、共享仓写入。

### P2｜批量一键对齐 + 一致性报告（约 2–3 h）

- P2.1 `align-all-platforms`（§5），含"任一平台失败即停"与逐平台回滚状态。
- P2.2 `version-alignment-report`（只读）：三列差（vs 锚定代 / vs 共享 current / 内部是否自洽）+ 软件面三态。
- 判据：六平台表一次出全；dsh 报"已对齐"、其它五家报出各自的差与受影响键；报告**不把"落后"判成失败**。

### P3｜软件面：绑定状态判定 + 半自动导入（约 3 h，视件数）

- P3.1 只读三态判定（§6 层 1），**带缓存**（路径+大小+mtime → 上次哈希），避免每次全量哈希大二进制。
- P3.2 对未绑定/不符的件走既有导入流程（§6 层 2），每件一个 plan、逐件确认。
- 判据：六平台 × 六件的三态表可回读；至少一件经导入后 `version` 能力真调用返回 `exitCode 0`，且 `actions.mjs:20-21` 的哈希核对通过。

### P4｜外部安装位的裁定（可选，约 1 h）

- 议题：`<local-tool-body-path> 这类平台自选外部安装位，与配方声明的 `${platformRuntime}/software/<id>` 不符。两条路：① 允许"外部位"作为**显式登记**的合法形态（写进绑定记录并在报告里标 `external`）；② 要求一律迁进平台 runtime。
- 这是**架构裁定**，不是实现细节，需你定；定了之后 P3 的报告口径随之固定。

## 八、待你裁定 / 待你提供

1. **锚定件落点**：甲案（工作区 `versions/锚定代.json`）还是乙案（管理台仓内冻结）。
2. **锚定代内容**：是否就取 §3.1 那套（= dsh 现用，引擎自述与检查器自洽）；`platform-conformance` 用已发布最新 `1.5.1` 还是另钉。
3. **软件本体源**：层 2 需要你给"安装源路径"（安装包或已装目录）。**没有源，本体永远绑定不了** —— 这是 BP-1 的硬约束，不是实现难度。
4. **P4 的外部安装位**：允许登记还是要求迁入平台 runtime。
5. **先做哪个 P**：建议 P1（做完你就能一键对齐任一平台并自动验证），批量化与软件面随后。
