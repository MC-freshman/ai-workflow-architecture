## 0. 进入条件

1. 读取 `AI_ARCHITECTURE_SYSTEM_PROMPT.md`、`agentic-workflow-master-manual.md`、`versions/架构基本原则.md` 和 3.3.0 当前状态。
2. 3.3.0 的 skill/agent 更新不在本轮重做；管理台作为 3.4.0 独立变更线。
3. 不在 `E:\ai` 创建新的正式一级目录。管理台源代码放在工作区之外的独立产品目录或独立仓库；本轮先完成架构目录内的方案、配置契约和可回读证据。
4. 默认只读扫描。任何写入必须经过 plan→apply→verify，任何破坏性动作前必须有 checkpoint。
5. 不改已发布 tool、agent、software 字节；不改共享 current；不移动或删除现有平台目录、runtime、凭据和软件本体。
6. 运行测试使用临时 fixture 或用户明确选择的工作区副本；不使用 `E:\ai` 的生产版本做破坏性试验。
7. 所有 P 约 2–3 小时，每个 P 分为 2–4 个子块；每个子块结束时都有可回读产物，可以安全停手。

## 2. P 步的具体实现口径

### P0：边界冻结

固定以下不变式：

- 一个管理台实例只绑定一个当前工作区，但允许用户切换到另一个已授权工作区；
- 工作区路径必须规范化并落在用户明确选择的根内；
- 管理台缓存不属于架构仓库；
- 发布目录只读；写入只能针对 staging、current 指针或治理文档，并有计划；
- 管理台不改变其他用户、不连接中心服务、不读外部 runtime。

### P1：扫描器

扫描器必须输出机器可读 JSON 和用户可读 HTML 两份结果。每个对象带：`id`、`kind`、`sourcePath`、`version`、`hash`、`resolvedFrom`、`status`、`evidencePath`。任何“看起来存在但无法校验”的资源进入 `unverified`，不进入绿色计数。

### P3/P4：计划和文档

计划文件必须带：计划 ID、工作区 ID、生成时间、基线哈希、文件变更清单、预期验证、回滚点和状态。执行期间发现非阻断缺陷只登记，不在同一 P 内扩范围。架构基本原则和当前基线的修改需要单独的高敏感确认页。

### P5：软件中心

软件中心复用 3.2.0 的连接器语义：一个共享连接器、多份软件声明、少量特殊 adapter。软件没有原生 MCP 就不虚构 MCP；GUI 需要人工时返回结构化状态；本体、凭据、缓存和日志只存在本机平台 runtime 或登记路径。

### P6：Git 和 GitHub

GitHub 是每个用户自己的远端。管理台只显示和操作当前用户显式绑定的远端，不保存共享账号。推送、删除远端分支、修改保护分支等操作必须显示目标、提交范围和风险，再由用户点击确认。

## 3. 最小验收集

最终只保留能抓真失败的检查，并集中到一次收口命令或等价的单一报告：

1. `inventory-readback`：三仓、平台、软件、文档和 Git 读数与文件逐项一致；
2. `plan-safety`：越界路径、外部改动、已发布覆盖、凭据和大文件均在写入前拒绝；
3. `resource-flow`：资源新增、版本比较、停用、current 计划和回滚闭环；
4. `docs-flow`：文档编辑、构建、断链、排版回读和逐字回滚；
5. `software-flow`：CLI 与 GUI/会话软件健康检查或真实启动/关闭闭环；
6. `git-flow`：个人仓库提交、敏感扫描、推送预览、备份和恢复演练；
7. `package-flow`：安装版、便携版、首次启动和无残留退出；
8. `conform`：架构现有机器判定仍通过，新增管理台报告不制造空行假绿。

## 4. 用户必须亲自完成的动作

日常管理不需要命令行。只有以下动作必须由用户在界面确认或提供信息：

- 首次选择自己的架构工作区；
- 绑定个人 GitHub 远端或登录 Git Credential Manager；
- 允许软件启动、外网访问、提权、GUI 交互或凭据引用；
- 确认提交、推送、回滚和修改顶层治理文件。

这些确认会记录摘要，不记录密码、令牌或软件本体内容。

## 5. 非阻断缺陷和维护期

执行期出现但不影响本表判据的事项只记录现象、复现条件、影响面、初步定位和建议处置，统一写入 `3.4.0-LEDGER.md` 的维护区。典型项目包括：不同 Windows 版本的显示差异、个别 GUI 软件的窗口状态检测、GitHub 企业版登录差异、未冻结软件快照和文档站的进一步美化。它们不能反向提高本轮 P 的通过门槛。

## 6. 收口报告固定内容

收口报告必须包含：

1. P0–P9 的产物路径、执行时间和判定；
2. 管理台版本、架构基线版本和工作区 ID；
3. 安装版/便携版文件哈希和启动回归读数；
4. 平台、资源、软件、文档和 Git 的最终 inventory 摘要；
5. 软件真实健康/启动/拒绝边界证据；
6. 备份恢复演练和回滚提交；
7. 凭据、本体、大文件扫描结果；
8. HEAD SHA、白名单内 `git status`、远端与本地一致性、入库时间；
9. 维护期缺陷和未纳入范围的事项。
